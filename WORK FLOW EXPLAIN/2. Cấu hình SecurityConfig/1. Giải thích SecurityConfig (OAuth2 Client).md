# Giải thích `SecurityConfig` — OAuth2 Client (Phase 2)

## 0. Vì sao file này "ngắn mà khó hiểu"?

`SecurityConfig` chỉ khoảng 90 dòng, nhưng đọc xong vẫn không hiểu "sao nhiêu đây mà chạy được cả luồng OAuth2". Lý do:

> Phần lớn cơ chế OAuth2 **không nằm trong file này**. Nó nằm ở các **bean và filter mà Spring Security tự tạo ẩn** (endpoint chuyển hướng, filter callback, kho lưu token theo session, bộ resolve tham số controller...). `SecurityConfig` của chúng ta chỉ làm nhiệm vụ **bật các thứ đó lên và tùy biến vài chỗ**.

Giống như tảng băng trôi: code bạn thấy là phần nổi, cơ chế thật là phần chìm.

```
      SecurityConfig  (phần NỔI — bạn viết, ~90 dòng)
 ─────────────────────────────────────────────────────
      Bean & Filter Spring tự tạo  (phần CHÌM — cơ chế thật)
```

Tài liệu này đi theo 3 tầng:
1. **Tầng 1** — Các thành phần **HIỆN** trong `SecurityConfig` và vai trò của chúng.
2. **Tầng 2** — Các thành phần **ẨN** do Spring auto-config, mà config của ta móc vào.
3. **Tầng 3** — Chúng phối hợp ra sao trong **từng chức năng** của dự án.

---

## 1. Bức tranh tổng thể

Có 3 nhóm thành phần. Đọc từ trên xuống: nhóm trên **cung cấp dữ liệu / được dùng bởi** nhóm dưới.

```
NHÓM A — Spring tạo từ file cấu hình
┌────────────────────────────────────────────────────────────┐
│  application.properties  →  ClientRegistrationRepository   │
│  (giữ thông tin client tên "google": id, secret, scope,    │
│   redirect-uri, authorization-uri, token-uri)              │
└────────────────────────────────────────────────────────────┘
                     (mọi thứ bên dưới tra cứu client ở đây)

NHÓM B — BẠN viết trong SecurityConfig  (chỉ 2 thứ)
┌────────────────────────────────────────────────────────────┐
│  1) oauth2Client() + authorizationRequestResolver          │
│     → bật OAuth2 Client, thêm PKCE + xin refresh token     │
│  2) @Bean OAuth2AuthorizedClientManager (.refreshToken())  │
│     → bật auto-refresh access token                        │
└────────────────────────────────────────────────────────────┘

NHÓM C — Spring TỰ tạo ẩn  (bạn không thấy trong code)
┌──────────────────────────────────────────────────────────────┐
│  • 2 endpoint:  /oauth2/authorization/google  (chặng ĐI)     │
│                 /login/oauth2/code/google     (chặng VỀ)     │
│  • 2 filter:    RedirectFilter | CodeGrantFilter             │
│  • OAuth2AuthorizedClientRepository  (lưu token theo session)│
│  • Bộ resolve cho @RegisteredOAuth2AuthorizedClient          │
└──────────────────────────────────────────────────────────────┘
```

**Cách các nhóm phối hợp** — vòng đời một request, đi **một chiều từ trên xuống**:

```
(1) Browser gọi 1 trang cần token, ví dụ  GET /connected
        │
        ▼
(2) Controller cần token → hỏi OAuth2AuthorizedClientManager
        │        "đã có token 'google' chưa?"  →  CHƯA
        ▼
(3) Ném ClientAuthorizationRequiredException
        │
        ▼
(4) RedirectFilter bắt exception → build request (PKCE, state, offline)
        │                        → 302 redirect sang Google
        ▼
(5) Người dùng đăng nhập Google + bấm "Cho phép"
        │
        ▼
(6) Google gọi lại:  GET /login/oauth2/code/google?code=...&state=...
        │
        ▼
(7) CodeGrantFilter: kiểm tra state → đổi code lấy token
        │            → lưu token vào session
        ▼
(8) 302 redirect về trang gốc /connected  (lần này ĐÃ có token)
        │
        ▼
(9) Controller chạy thật → đọc token → render trang
```

Ghi nhớ: **chỉ bước (4) và (7) là "phần chìm"** Spring lo; bạn chỉ cấu hình *cách* nó build request (bước 4) và *cách* refresh (dùng ở các request sau).

## 2. TẦNG 1 — Các thành phần HIỆN trong `SecurityConfig`

### 2.1. `SecurityFilterChain` + `permitAll()`

> **Khái niệm:** `SecurityFilterChain` là **chuỗi các Servlet Filter của Spring Security** mà mọi HTTP request phải đi qua trước khi tới controller. Nó **chịu trách nhiệm định nghĩa "luật bảo mật"** cho ứng dụng: URL nào được vào, bật/tắt tính năng nào (CSRF, login, oauth2Client...). Ta khai báo nó dưới dạng một `@Bean` và cấu hình qua đối tượng `HttpSecurity`.
>
> `permitAll()` là một **quy tắc phân quyền** (authorization rule), chịu trách nhiệm cho phép **mọi request truy cập mà không cần authentication**.

```java
@Bean
public SecurityFilterChain filterChain(
        HttpSecurity http,
        ClientRegistrationRepository clientRegistrationRepository) throws Exception {
    http
            // Không bắt login: mọi request đều được phép; ủy quyền chỉ kích hoạt khi cần token
            .authorizeHttpRequests(auth -> auth.anyRequest().permitAll())
            .oauth2Client(oauth2 -> oauth2
                    .authorizationCodeGrant(codeGrant -> codeGrant
                            .authorizationRequestResolver(
                                    pkceAuthorizationRequestResolver(clientRegistrationRepository))
                    )
            );
    return http.build();
}
```

**Vai trò:** đây là "bộ luật" cho mọi HTTP request đi qua Spring Security.

- `authorizeHttpRequests(... permitAll())`: **không bắt đăng nhập** cho bất kỳ URL nào.
  - Vì sao? Vì đây là **delegated authorization**, không phải login. Ta **không** muốn Spring chặn `/`, `/calendars`... và đá về trang login. Việc "xin quyền Google" sẽ được kích hoạt **đúng lúc controller cần token** (bước 2–3 ở sơ đồ trên), chứ không phải chặn ngay từ đầu.
- Tham số `ClientRegistrationRepository clientRegistrationRepository`: **Spring tự inject** (xem [Tầng 2 - 3.1](#31-clientregistrationrepository--từ-applicationproperties)). Ta chỉ nhận vào để đưa cho resolver.

> ⚠️ Phân biệt: `permitAll()` KHÔNG có nghĩa "tắt bảo mật". Nó chỉ nói "không yêu cầu authentication để vào URL". Cơ chế OAuth2 vẫn hoạt động đầy đủ ở lớp `oauth2Client()`.

### 2.2. `oauth2Client()`

> **Khái niệm:** `oauth2Client()` là một **cấu hình (DSL) trên `HttpSecurity`**, chịu trách nhiệm **bật vai trò "OAuth2 Client"** cho ứng dụng — tức cho phép app **xin, giữ và dùng token để gọi API thay mặt người dùng**, mà KHÔNG đăng nhập người dùng vào app. Bên trong nó, `.authorizationCodeGrant()` là **cấu hình con** chịu trách nhiệm khai báo dùng luồng **Authorization Code Grant** và cho phép cắm resolver tùy biến.

```java
.oauth2Client(oauth2 -> oauth2
        .authorizationCodeGrant(codeGrant -> codeGrant
                .authorizationRequestResolver(...)))
```

**Vai trò:** bật tính năng **OAuth2 Client** (khác với `oauth2Login()`).

| | `oauth2Client()` | `oauth2Login()` |
|---|---|---|
| Mục tiêu | Xin **quyền gọi API** thay người dùng | **Đăng nhập** người dùng vào app |
| Tạo `Authentication`/principal? | **Không** | Có |
| Bản chất | Delegated authorization (OAuth2) | Xác thực danh tính (OIDC) |
| Dự án này | ✅ dùng cái này | ❌ |

Chọn `oauth2Client()` đúng với tinh thần dự án: app được **ủy quyền** đọc Google Calendar, chứ không "đăng nhập bằng Google".

`.authorizationCodeGrant(...)` khai báo dùng **Authorization Code Grant**, và cho phép ta cắm một `authorizationRequestResolver` tùy biến vào.

### 2.3. `authorizationRequestResolver` — vì sao cần tùy biến?

> **Khái niệm:** `OAuth2AuthorizationRequestResolver` là **thành phần chịu trách nhiệm dựng nội dung của "authorization request"** — tức tập hợp tham số (`client_id`, `redirect_uri`, `scope`, `state`, và ở đây thêm PKCE + `access_type`/`prompt`) sẽ được gửi sang Authorization Server. `DefaultOAuth2AuthorizationRequestResolver` là **bản cài đặt sẵn** của interface đó; ta tùy biến nó qua `setAuthorizationRequestCustomizer(...)` để thêm PKCE và tham số xin refresh token.

Mặc định Spring đã build được authorization request cơ bản (client_id, redirect_uri, scope, state...). Nhưng dự án cần thêm **2 thứ mặc định KHÔNG có**:

1. **PKCE** (`code_challenge` + `code_challenge_method=S256`) — với confidential client, Spring không tự bật.
2. **Xin refresh token** — Google yêu cầu thêm `access_type=offline` và `prompt=consent`.

Vì vậy ta thay resolver mặc định bằng resolver tự cấu hình:

```java
private OAuth2AuthorizationRequestResolver pkceAuthorizationRequestResolver(
        ClientRegistrationRepository repo) {
    DefaultOAuth2AuthorizationRequestResolver resolver =
            new DefaultOAuth2AuthorizationRequestResolver(repo, "/oauth2/authorization");

    resolver.setAuthorizationRequestCustomizer(builder -> {
        OAuth2AuthorizationRequestCustomizers.withPkce().accept(builder);   // (1) PKCE
        builder.additionalParameters(params -> {                            // (2) xin refresh token
            params.put("access_type", "offline");
            params.put("prompt", "consent");
        });
    });
    return resolver;
}
```

Giải thích từng phần:

- `new DefaultOAuth2AuthorizationRequestResolver(repo, "/oauth2/authorization")` → Khởi tạo `DefaultOAuth2AuthorizationRequestResolver` và cấu hình rằng **mọi request có dạng `/oauth2/authorization/{registrationId}`** sẽ sử dụng resolver này để tạo `OAuth2AuthorizationRequest`. Ví dụ, khi người dùng truy cập `/oauth2/authorization/google`, Spring sẽ lấy `ClientRegistration` có `registrationId = "google"`, xây dựng Authorization Request (gồm `client_id`, `redirect_uri`, `scope`, `state`, ...), sau đó **OAuth2AuthorizationRequestRedirectFilter** redirect trình duyệt sang Google để bắt đầu Authorization Code Flow.
- `OAuth2AuthorizationRequestCustomizers.withPkce()`
  → tự sinh `code_verifier` (bí mật, lưu trong session cùng authorization request) và gắn `code_challenge = SHA256(code_verifier)` + `code_challenge_method=S256` vào request. **Đây chính là thứ thay thế cho `PkceUtil` viết tay ở Phase 1.**
- `additionalParameters(... access_type=offline, prompt=consent)`
  → 2 tham số riêng của Google để chắc chắn nhận được **refresh token**.

> 💡 Ở Phase 1 ta tự sinh state + PKCE + tự ghép query string. Ở Phase 2, tất cả gói gọn trong resolver này.

### 2.4. Bean `OAuth2AuthorizedClientManager` — bật tự động quản lí Access Token

> **Trước hết, cần hiểu `OAuth2AuthorizedClient` là gì.**

`OAuth2AuthorizedClient` là object đại diện cho **một OAuth2 Client đã được người dùng cấp quyền (authorized)**. Nó chứa toàn bộ thông tin cần thiết để ứng dụng tiếp tục gọi Resource Server thay mặt người dùng, bao gồm:

- `ClientRegistration` (thông tin ứng dụng đã đăng ký với Authorization Server) - Xem phần 3.1
- `AccessToken`
- `RefreshToken` (nếu được cấp)

Có thể hình dung như sau:

```
OAuth2AuthorizedClient
│
├── ClientRegistration
├── AccessToken
└── RefreshToken
```

Sau khi người dùng hoàn thành **Authorization Code Flow**, Spring sẽ tạo một `OAuth2AuthorizedClient` và lưu nó lại để các request sau có thể tái sử dụng Access Token hoặc Refresh Token, thay vì bắt người dùng đăng nhập Google lại từ đầu.

Mặc định, Spring Security sử dụng **`AuthenticatedPrincipalOAuth2AuthorizedClientRepository`** để quản lý việc lưu và đọc `OAuth2AuthorizedClient`.

Repository này hoạt động theo hai trường hợp:

- **Nếu người dùng đã được xác thực bởi Spring Security** (đã có `Authentication` trong `SecurityContext`), `OAuth2AuthorizedClient` sẽ được lưu và tra cứu theo **principal** (người dùng đã đăng nhập).
- **Nếu request là anonymous** (chưa có `Authentication`), `AuthenticatedPrincipalOAuth2AuthorizedClientRepository` sẽ **ủy quyền (delegate)** việc lưu và đọc dữ liệu cho **`HttpSessionOAuth2AuthorizedClientRepository`**.

Trong dự án này, ứng dụng **không sử dụng cơ chế đăng nhập (Login) của Spring Security** mà chỉ tận dụng Spring Security để thực hiện OAuth2 Authorization Code Flow. Vì vậy, sau khi hoàn tất quá trình OAuth2, request vẫn được xem là **anonymous**.

Do đó, `AuthenticatedPrincipalOAuth2AuthorizedClientRepository` sẽ tự động **ủy quyền** cho `HttpSessionOAuth2AuthorizedClientRepository`, và `OAuth2AuthorizedClient` sẽ được lưu trong **HttpSession**.

Có thể hình dung như sau:

```
Browser
    │
JSESSIONID = ABC123
    │
    ▼
HttpSession
│
└── OAuth2AuthorizedClient
      ├── ClientRegistration
      ├── AccessToken
      └── RefreshToken
```

Mỗi trình duyệt sẽ có một `JSESSIONID` riêng, tương ứng với một `HttpSession` riêng. Vì vậy:

- Browser A có một `OAuth2AuthorizedClient` riêng.
- Browser B có một `OAuth2AuthorizedClient` riêng.
- Access Token và Refresh Token của các browser không ảnh hưởng hay ghi đè lẫn nhau.

Khi một request mới được gửi lên từ cùng trình duyệt (cùng `JSESSIONID`), Spring sẽ đọc lại `OAuth2AuthorizedClient` từ `HttpSession` để tiếp tục sử dụng Access Token hoặc Refresh Token nếu cần.

----

> **`OAuth2AuthorizedClientManager` là gì?**

`OAuth2AuthorizedClientManager` là **thành phần điều phối trung tâm** chịu trách nhiệm đảm bảo ứng dụng luôn có một `OAuth2AuthorizedClient` hợp lệ để sử dụng.

Khi một controller hoặc service cần gọi API của Resource Server, thay vì tự kiểm tra Access Token còn hạn hay không, tự refresh token hay tự thực hiện Authorization Code Flow, nó chỉ cần yêu cầu `OAuth2AuthorizedClientManager` cung cấp một `OAuth2AuthorizedClient`.

Lúc này, Manager sẽ thực hiện các bước sau:

- Kiểm tra xem đã có `OAuth2AuthorizedClient` cho người dùng hiện tại hay chưa.
- Nếu đã có và Access Token vẫn còn hiệu lực, trả về ngay.
- Nếu Access Token đã hết hạn nhưng có Refresh Token, sử dụng Refresh Token để lấy Access Token mới.
- Nếu chưa có `OAuth2AuthorizedClient`, giao cho `AuthorizationCodeOAuth2AuthorizedClientProvider` xử lý. **Provider** sẽ ném `ClientAuthorizationRequiredException` để khởi động **Authorization Code Flow**.

Nói cách khác, `OAuth2AuthorizedClientManager` **không trực tiếp thực hiện việc lấy hay refresh Access Token**, mà chỉ **điều phối** và quyết định nên sử dụng chiến lược nào để có được một `OAuth2AuthorizedClient` hợp lệ. Việc thực thi sẽ được **ủy quyền** cho các `OAuth2AuthorizedClientProvider`, trong đó mỗi Provider chỉ phụ trách **một cơ chế cấp hoặc làm mới Access Token**:

- **`AuthorizationCodeOAuth2AuthorizedClientProvider`**: xử lý việc **khởi động Authorization Code Flow**. Nếu chưa có `OAuth2AuthorizedClient`, Provider sẽ ném `ClientAuthorizationRequiredException` để `OAuth2AuthorizationRequestRedirectFilter` chuyển hướng người dùng sang Authorization Server. Sau khi người dùng cấp quyền, việc trao đổi **Authorization Code** lấy **Access Token** sẽ do `OAuth2AuthorizationCodeGrantFilter` đảm nhiệm.

- **`RefreshTokenOAuth2AuthorizedClientProvider`**: xử lý **Refresh Token Grant**, tức là sử dụng **Refresh Token** để lấy **Access Token** mới khi Access Token hiện tại đã hết hạn.
- **`ClientCredentialsOAuth2AuthorizedClientProvider`**: xử lý **Client Credentials Grant**, dùng khi ứng dụng tự xác thực để lấy Access Token mà không có người dùng tham gia.
- ...

Hoặc có thể hình dung mối quan hệ giữa `Manager` và các `Provider` như sau:

```
Controller / Service
        │
        │ authorize(...)
        ▼
OAuth2AuthorizedClientManager
        │
        ├── Chưa có Authorized Client
        │       ▼
        │  AuthorizationCodeOAuth2AuthorizedClientProvider
        │
        ├── Access Token hết hạn
        │       ▼
        │  RefreshTokenOAuth2AuthorizedClientProvider
        │
        └── (Các Grant Type khác...)
```

```java
@Bean
public OAuth2AuthorizedClientManager authorizedClientManager(
        ClientRegistrationRepository clientRegistrationRepository,
        OAuth2AuthorizedClientRepository authorizedClientRepository) {

    OAuth2AuthorizedClientProvider provider =
            OAuth2AuthorizedClientProviderBuilder.builder()
                    .authorizationCode()   // cho phép khởi động Authorization Code flow
                    .refreshToken()        // cho phép dùng refresh_token đổi access token mới
                    .build();

    DefaultOAuth2AuthorizedClientManager manager =
            new DefaultOAuth2AuthorizedClientManager(
                    clientRegistrationRepository, authorizedClientRepository);
    manager.setAuthorizedClientProvider(provider);
    return manager;
}
```

### Giải thích từng phần

- **`ClientRegistrationRepository clientRegistrationRepository`** → Repository chứa toàn bộ các `ClientRegistration` (Google, GitHub, Microsoft, ...). Khi cần thực hiện Authorization Code Flow hoặc Refresh Token, `OAuth2AuthorizedClientManager` sẽ lấy cấu hình của OAuth2 Client (clientId, clientSecret, tokenUri, redirectUri, ...) từ Repository này.
- **`OAuth2AuthorizedClientRepository authorizedClientRepository`** → Repository dùng để lưu và đọc `OAuth2AuthorizedClient` của người dùng hiện tại. Trong dự án này, Repository mặc định sẽ lưu `OAuth2AuthorizedClient` trong `HttpSession`, nhờ đó Access Token và Refresh Token được tái sử dụng giữa các request.
- **`OAuth2AuthorizedClientProvider provider = ...`** → Tạo tập hợp các **chiến lược (Provider)** mà `OAuth2AuthorizedClientManager` được phép sử dụng. Mỗi Provider chịu trách nhiệm cho một OAuth2 Grant Type khác nhau.
- **`.authorizationCode()`** → Đăng ký `AuthorizationCodeOAuth2AuthorizedClientProvider`. Nếu người dùng **chưa có `OAuth2AuthorizedClient`**, Manager sẽ sử dụng Provider này để **khởi động Authorization Code Flow**. Provider sẽ ném `ClientAuthorizationRequiredException` để `OAuth2AuthorizationRequestRedirectFilter` chuyển hướng người dùng sang Authorization Server. Sau khi người dùng cấp quyền, việc **trao đổi Authorization Code lấy Access Token** sẽ được `OAuth2AuthorizationCodeGrantFilter` thực hiện.
- **`.refreshToken()`** → Đăng ký `RefreshTokenOAuth2AuthorizedClientProvider`. Khi Access Token đã hết hạn nhưng vẫn còn Refresh Token, Manager sẽ sử dụng Provider này để tự động gọi Token Endpoint lấy Access Token mới mà không yêu cầu người dùng đăng nhập hoặc consent lại.
- **`new DefaultOAuth2AuthorizedClientManager(...)`** → Khởi tạo `OAuth2AuthorizedClientManager` với hai thành phần quan trọng:
    - `ClientRegistrationRepository`: nơi lấy cấu hình OAuth2 Client.
    - `OAuth2AuthorizedClientRepository`: nơi lưu và đọc `OAuth2AuthorizedClient`.
- **`manager.setAuthorizedClientProvider(provider)`** → Gắn các Provider vừa cấu hình vào Manager. Kể từ thời điểm này, mỗi khi có yêu cầu lấy `OAuth2AuthorizedClient`, Manager sẽ lần lượt sử dụng các Provider đã đăng ký để quyết định nên:
    - sử dụng Access Token hiện tại,
    - refresh Access Token,
    - hay khởi động Authorization Code Flow.

**Vai trò:** đây là "bộ não" quyết định *lấy token ở đâu / có cần refresh không* mỗi khi controller hỏi tới token.

- `.authorizationCode()`: nếu **chưa** có token → cho phép kích hoạt flow xin quyền (ném `ClientAuthorizationRequiredException` để filter redirect sang Google).
- `.refreshToken()`: nếu token **hết hạn** và có refresh token → tự động gọi token endpoint đổi access token mới, **không bắt người dùng consent lại**. Đây chính là thứ thay thế cho `TokenService.getValidAccessToken()` viết tay ở Phase 1.

> Nếu **không** khai bean này, `@RegisteredOAuth2AuthorizedClient` vẫn chạy được nhưng ta mất quyền kiểm soát rõ ràng việc bật `refreshToken()`. Khai tường minh để đảm bảo auto-refresh hoạt động.

## 3. TẦNG 2 — Các thành phần ẨN (Spring auto-config) mà config móc vào

Đây là phần "chìm" giúp `SecurityConfig` ngắn gọn.

### 3.1. `ClientRegistrationRepository` — từ `application.properties`

> **Khái niệm:** `ClientRegistration` là **object mô tả toàn bộ cấu hình đăng ký của MỘT provider** (client-id, client-secret, scope, grant type, redirect-uri, các endpoint authorization/token...). `ClientRegistrationRepository` là **kho chứa các `ClientRegistration`**, chịu trách nhiệm **tra cứu chúng theo `registrationId`** (ví dụ `"google"`). Bản mặc định là `InMemoryClientRegistrationRepository`.

Ta **không** tạo object này. Spring Boot đọc các dòng sau và tự tạo:

```properties
spring.security.oauth2.client.registration.google.client-id=${GOOGLE_CLIENT_ID}
spring.security.oauth2.client.registration.google.client-secret=${GOOGLE_CLIENT_SECRET}
spring.security.oauth2.client.registration.google.scope=https://www.googleapis.com/auth/calendar.readonly
spring.security.oauth2.client.registration.google.authorization-grant-type=authorization_code
spring.security.oauth2.client.registration.google.redirect-uri={baseUrl}/login/oauth2/code/{registrationId}
spring.security.oauth2.client.provider.google.authorization-uri=https://accounts.google.com/o/oauth2/v2/auth
spring.security.oauth2.client.provider.google.token-uri=https://oauth2.googleapis.com/token
```

→ Spring gom lại thành một `ClientRegistration` tên **`google`**, cất trong `ClientRegistrationRepository` (bản `InMemory...`). Mọi filter/manager phía sau tra cứu client theo `registrationId = "google"` ở đây.

> Vì sao scope **không có `openid`**? Có `openid` → Spring hiểu là OIDC (login) và sẽ dựng ID token/principal. Ta chỉ để `calendar.readonly` để giữ đúng bản chất OAuth2 thuần.

### 3.2. Hai endpoint TỰ SINH (không có controller nào cho chúng)

> **Khái niệm:** đây là **2 URL do Spring Security tự đăng ký và tự xử lý bằng filter** (không phải `@GetMapping` trong controller). Một cái chịu trách nhiệm **khởi động** flow (chặng ĐI), một cái chịu trách nhiệm **nhận kết quả** từ Google (chặng VỀ).

| Endpoint | Ai xử lý | Nhiệm vụ |
|----------|----------|----------|
| `/oauth2/authorization/google` | `OAuth2AuthorizationRequestRedirectFilter` | Khởi động flow: build request + redirect sang Google |
| `/login/oauth2/code/google` | `OAuth2AuthorizationCodeGrantFilter` | Nhận callback từ Google: đổi code lấy token |

> Tìm trong project sẽ **không thấy** `@GetMapping("/login/oauth2/code/google")` — vì nó do filter xử lý, không phải controller. Đây là lý do lớn khiến người mới thấy "khó hiểu".
> URL `/login/oauth2/code/google` phải trùng với **Authorized redirect URI** khai trên Google Cloud Console.

### 3.3. Hai filter cốt lõi

> **Khái niệm:** cả hai đều là **Servlet Filter** nằm trong `SecurityFilterChain`. Đây chính là "phần chìm" thực thi luồng Authorization Code: một filter lo **chặng ĐI** (đẩy user sang Google), một filter lo **chặng VỀ** (nhận code, đổi token).

### **a) `OAuth2AuthorizationRequestRedirectFilter` — chặng ĐI** (bước 4 ở sơ đồ mục 1)

`OAuth2AuthorizationRequestRedirectFilter` là **Servlet Filter** chịu trách nhiệm **khởi động Authorization Code Flow**. Nhiệm vụ của nó là tạo `OAuth2AuthorizationRequest` và chuyển hướng (redirect) trình duyệt sang Authorization Server (Google).

Filter này có thể được kích hoạt theo **hai cách**:

- **Người dùng truy cập trực tiếp** vào endpoint:

```
GET /oauth2/authorization/google
```

Đây là **authorization-request endpoint** dùng chung cho cả `oauth2Client` lẫn `oauth2Login`.

- **Hoặc** một controller/service gọi `OAuth2AuthorizedClientManager`, nhưng phát hiện **chưa có `OAuth2AuthorizedClient`**. Lúc này `AuthorizationCodeOAuth2AuthorizedClientProvider` sẽ ném ra `ClientAuthorizationRequiredException`. Exception này được `OAuth2AuthorizationRequestRedirectFilter` bắt lại để khởi động Authorization Code Flow.

Sau khi được kích hoạt, Filter sẽ thực hiện các bước sau:

1. Gọi `OAuth2AuthorizationRequestResolver` (đã cấu hình ở mục **2.3**) để tạo một `OAuth2AuthorizationRequest`. Trong dự án này, request sẽ được bổ sung:
    - `state`
    - PKCE (`code_challenge`, `code_challenge_method`)
    - `access_type=offline`
    - `prompt=consent`
2. Lưu `OAuth2AuthorizationRequest` vào `AuthorizationRequestRepository` (mặc định là `HttpSessionOAuth2AuthorizationRequestRepository`). Mục đích là để callback sau này có thể:
    
    - đối chiếu `state` nhằm chống CSRF,
    - lấy lại `code_verifier` của PKCE,
    - biết Authorization Request ban đầu để tiếp tục hoàn thành Authorization Code Flow.
    
    `HttpSessionOAuth2AuthorizationRequestRepository` **không có cơ chế lưu trữ riêng**, mà chỉ sử dụng **`HttpSession` của người dùng** để lưu dữ liệu. Thực chất, Repository này chỉ đóng vai trò là lớp bao bọc (wrapper) cho `HttpSession`, thực hiện việc lưu và đọc `OAuth2AuthorizationRequest` thông qua các thao tác tương đương:
    
    ```
    session.setAttribute(KEY, authorizationRequest);
    ```
    
    và
    
    ```
    session.getAttribute(KEY);
    ```
    
    Có thể hình dung Session của người dùng lúc này như sau:
    
    ```
    Browser
        │
    JSESSIONID = ABC123
        │
        ▼
    HttpSession
    │
    ├── SPRING_SECURITY_SAVED_AUTHORIZATION_REQUEST
    │      │
    │      ▼
    │   OAuth2AuthorizationRequest
    │        ├── state
    │        ├── code_verifier
    │        ├── redirect_uri
    │        └── ...
    │
    └── ...
    ```
    
    Nhờ được lưu trong **HttpSession của chính người dùng**, khi Google redirect trình duyệt quay trở lại (vẫn mang theo cùng `JSESSIONID`), `OAuth2AuthorizationCodeGrantFilter` có thể lấy lại đúng `OAuth2AuthorizationRequest` đã lưu để tiếp tục hoàn thành Authorization Code Flow.
    
3. Trả về HTTP **302 Redirect**, chuyển trình duyệt sang Authorization Server (Google).

   Toàn bộ quá trình có thể hình dung như sau:

   ```
   Browser
    │
   GET /oauth2/authorization/google
    │
    ▼
   OAuth2AuthorizationRequestRedirectFilter
    │
    ▼
   OAuth2AuthorizationRequestResolver
    │
    ▼
   OAuth2AuthorizationRequest
    │
    ▼
   AuthorizationRequestRepository
   (HttpSessionOAuth2AuthorizationRequestRepository)
    │
    ▼
   HttpSession
    │
    ▼
   302 Redirect
    │
    ▼
   Google Authorization Server
   ```

**b) `OAuth2AuthorizationCodeGrantFilter` — chặng VỀ** (bước 7 ở sơ đồ mục 1)

`OAuth2AuthorizationCodeGrantFilter` là **Servlet Filter** chịu trách nhiệm **hoàn tất Authorization Code Flow** sau khi người dùng đã đăng nhập và cấp quyền trên Authorization Server.

Filter này được kích hoạt khi Authorization Server (Google) redirect trình duyệt quay trở lại ứng dụng với callback:

```
GET /login/oauth2/code/google?code=...&state=...
```

Lúc này, Authorization Server đã cấp cho ứng dụng một **Authorization Code**, nhưng ứng dụng **chưa có Access Token**. Nhiệm vụ của Filter là sử dụng Authorization Code này để hoàn tất quá trình trao đổi và lấy Access Token.

Filter sẽ thực hiện lần lượt các bước sau:

1. **Lấy lại `OAuth2AuthorizationRequest` đã lưu trong `AuthorizationRequestRepository`** (mặc định là `HttpSessionOAuth2AuthorizationRequestRepository`).

    Khi Google redirect trình duyệt quay trở lại, browser vẫn gửi kèm **`JSESSIONID`** trong Cookie. Nhờ đó, Spring xác định được đúng `HttpSession` của người dùng.

    `HttpSessionOAuth2AuthorizationRequestRepository` sẽ sử dụng `JSESSIONID` để lấy lại `HttpSession`, sau đó đọc `OAuth2AuthorizationRequest` đã được lưu ở bước **OAuth2AuthorizationRequestRedirectFilter** thông qua thao tác tương đương:

    ```
    session.getAttribute(KEY);
    ```

    Có thể hình dung như sau:

    ```
    Browser
       │
    Cookie: JSESSIONID = ABC123
       │
       ▼
    HttpSession
    │
    ├── SPRING_SECURITY_SAVED_AUTHORIZATION_REQUEST
    │      │
    │      ▼
    │   OAuth2AuthorizationRequest
    │        ├── state
    │        ├── code_verifier
    │        ├── redirect_uri
    │        └── ...
    │
    └── ...
    ```
    
    Từ object này, Spring lấy được:
    
    - `state` ban đầu để đối chiếu với `state` trong callback (chống CSRF).
    - `code_verifier` đã sinh ở bước PKCE để sử dụng khi đổi token.
    - các thông tin của Authorization Request ban đầu.
2. **Kiểm tra `state`.**
    
    Nếu `state` trong callback không khớp với `state` đã lưu trong Session, Spring sẽ từ chối request vì có nguy cơ bị tấn công CSRF.
    
3. **Đổi Authorization Code lấy Access Token.**
    
    Filter sử dụng `OAuth2AccessTokenResponseClient` để gửi request đến **Token Endpoint** của Authorization Server, kèm theo:
    
    - Authorization Code
    - `code_verifier` (PKCE)
    - `client_id`
    - `client_secret` (nếu có)
    - `redirect_uri`
    
    Nếu thành công, Authorization Server sẽ trả về:
    
    - Access Token
    - Refresh Token (nếu được cấp)
    - thời gian hết hạn của Access Token
4. **Tạo và lưu `OAuth2AuthorizedClient`.**
    
    Spring đóng gói:
    
    - `ClientRegistration`
    - Access Token
    - Refresh Token
    
    thành một `OAuth2AuthorizedClient`, sau đó lưu vào `OAuth2AuthorizedClientRepository` để các request sau có thể tái sử dụng.
    
5. **Chuyển người dùng về ứng dụng.**
    
    Sau khi quá trình xác thực hoàn tất, Spring redirect người dùng về URL ban đầu mà họ đang truy cập trước khi bị chuyển sang Google.
    

    Có thể hình dung toàn bộ quá trình như sau:

    ```
    Google
     │
    302 Redirect
     │
    GET /login/oauth2/code/google?code=...&state=...
     │
     ▼
    OAuth2AuthorizationCodeGrantFilter
     │
     ├── Lấy AuthorizationRequest từ Session
     ├── Kiểm tra state
     ├── Đổi code lấy Access Token
     ├── Tạo OAuth2AuthorizedClient
     ├── Lưu vào OAuth2AuthorizedClientRepository
     ▼
    Redirect về ứng dụng
    ```

### 3.4. `OAuth2AuthorizedClientRepository` — nơi lưu trữ `OAuth2AuthorizedClient`

> **Tại sao cần thành phần này?**

Sau khi Spring hoàn thành **Authorization Code Flow**, ứng dụng sẽ nhận được:

- Access Token
- Refresh Token
- `ClientRegistration` tương ứng (Google, GitHub, ...)

Các thông tin này được đóng gói thành một `OAuth2AuthorizedClient`.

Nếu không lưu lại `OAuth2AuthorizedClient`, thì mỗi request mới đều phải thực hiện lại Authorization Code Flow, buộc người dùng phải đăng nhập và cấp quyền lại từ đầu.

Vì vậy, Spring cần một thành phần chịu trách nhiệm **lưu và đọc `OAuth2AuthorizedClient`** giữa các request.

Đó chính là vai trò của **`OAuth2AuthorizedClientRepository`**.

---

> **`OAuth2AuthorizedClientRepository` là gì?**

`OAuth2AuthorizedClientRepository` là interface chịu trách nhiệm **lưu, đọc và xóa** `OAuth2AuthorizedClient`.

Nó **không trực tiếp lưu dữ liệu**, mà chỉ định nghĩa cách quản lý `OAuth2AuthorizedClient`. Việc lưu ở đâu sẽ phụ thuộc vào implementation cụ thể.

---

### Mặc định Spring sử dụng gì?

Mặc định, Spring Security sử dụng:

```
AuthenticatedPrincipalOAuth2AuthorizedClientRepository
```

Đây là implementation mặc định của `OAuth2AuthorizedClientRepository`.

Repository này sẽ quyết định nơi lưu `OAuth2AuthorizedClient` dựa trên loại người dùng hiện tại.

- Nếu request đã được xác thực bởi Spring Security (đã có `Authentication`), `OAuth2AuthorizedClient` sẽ được lưu và tra cứu theo **principal** (người dùng đã đăng nhập).
- Nếu request là **anonymous** (chưa có `Authentication`), `AuthenticatedPrincipalOAuth2AuthorizedClientRepository` sẽ **ủy quyền (delegate)** việc lưu và đọc dữ liệu cho:

```
HttpSessionOAuth2AuthorizedClientRepository
```

---

### Tại sao dự án này lại dùng `HttpSessionOAuth2AuthorizedClientRepository`?

Trong dự án này, ứng dụng **không sử dụng cơ chế Login của Spring Security** mà chỉ sử dụng Spring Security để thực hiện OAuth2 Authorization Code Flow.

Do đó, sau khi hoàn tất OAuth2 Flow, request vẫn được xem là **anonymous**, nên `AuthenticatedPrincipalOAuth2AuthorizedClientRepository` sẽ tự động **ủy quyền** cho `HttpSessionOAuth2AuthorizedClientRepository`.

Repository này cũng giống như `HttpSessionOAuth2AuthorizationRequestRepository` ở phần trước: **nó không có nơi lưu trữ riêng**, mà chỉ sử dụng **`HttpSession` của người dùng** làm nơi lưu dữ liệu.

Về bản chất, nó thực hiện các thao tác tương đương:

```
session.setAttribute(KEY, authorizedClient);
```

```
session.getAttribute(KEY);
```

và

```
session.removeAttribute(KEY);
```

Có thể hình dung như sau:

```
Browser
    │
JSESSIONID = ABC123
    │
    ▼
HttpSession
│
└── OAuth2AuthorizedClient
      ├── ClientRegistration
      ├── AccessToken
      └── RefreshToken
```

Mỗi trình duyệt sẽ có một `JSESSIONID` riêng, tương ứng với một `HttpSession` riêng. Vì vậy:

- Browser A có `OAuth2AuthorizedClient` riêng.
- Browser B có `OAuth2AuthorizedClient` riêng.
- Access Token và Refresh Token của các browser không ảnh hưởng hay ghi đè lẫn nhau.

Khi một request mới được gửi lên từ cùng trình duyệt (cùng `JSESSIONID`), Spring sẽ đọc lại `OAuth2AuthorizedClient` từ `HttpSession`. Nhờ đó, `OAuth2AuthorizedClientManager` có thể:

- sử dụng ngay Access Token nếu vẫn còn hiệu lực;
- tự động Refresh Access Token nếu đã hết hạn;
- hoặc khởi động Authorization Code Flow nếu chưa có `OAuth2AuthorizedClient`.

### 3.5. `@RegisteredOAuth2AuthorizedClient` + `OAuth2AuthorizedClientArgumentResolver`

> **Khái niệm**: `@RegisteredOAuth2AuthorizedClient` là **annotation đánh dấu một tham số của method Controller**, báo cho Spring MVC biết:
> "Tham số này cần được truyền vào một `OAuth2AuthorizedClient` của registration tương ứng."

Ví dụ:

```java
@GetMapping("/calendars")
public String calendars(
        @RegisteredOAuth2AuthorizedClient("google")
        OAuth2AuthorizedClient client,
        Model model) {
    ...
}
```

Tuy nhiên, bản thân annotation **không tự tạo ra `OAuth2AuthorizedClient`**.

Việc tìm và tạo object này được thực hiện bởi **`OAuth2AuthorizedClientArgumentResolver`**.

Đây là một **`HandlerMethodArgumentResolver`** của Spring MVC.

---

>  `HandlerMethodArgumentResolver` là gì?

Trong Spring MVC, trước khi gọi một method của Controller, Spring phải chuẩn bị giá trị cho từng tham số của method.

Ví dụ:

```java
@GetMapping("/users/{id}")
public String detail(
        @PathVariable Long id,
        HttpServletRequest request,
        Model model) {
    ...
}
```

Spring phải biết:

- `id` lấy từ URL.
- `request` lấy từ Servlet Container.
- `model` do Spring tạo.

Việc quyết định **lấy giá trị ở đâu** cho từng tham số được giao cho các **`HandlerMethodArgumentResolver`**.

Mỗi Resolver chỉ chịu trách nhiệm xử lý một số kiểu tham số nhất định.

Ví dụ:

- `PathVariableMethodArgumentResolver` → xử lý `@PathVariable`
- `RequestParamMethodArgumentResolver` → xử lý `@RequestParam`
- `RequestResponseBodyMethodProcessor` → xử lý `@RequestBody`
- `ModelMethodProcessor` → xử lý `Model`
- `OAuth2AuthorizedClientArgumentResolver` → xử lý `@RegisteredOAuth2AuthorizedClient`

---

> `OAuth2AuthorizedClientArgumentResolver` hoạt động như thế nào?

Khi Spring MVC chuẩn bị gọi method của Controller, nó sẽ duyệt qua từng tham số và tìm `HandlerMethodArgumentResolver` phù hợp để tạo giá trị cho tham số đó.

Khi gặp tham số:

```java
@RegisteredOAuth2AuthorizedClient("google")
OAuth2AuthorizedClient client
```

Spring sẽ giao việc xử lý cho `OAuth2AuthorizedClientArgumentResolver`.

Resolver đọc `registrationId` từ annotation (ở đây là `"google"`), sau đó gọi `OAuth2AuthorizedClientManager` để yêu cầu một `OAuth2AuthorizedClient` hợp lệ.

Lúc này, `OAuth2AuthorizedClientManager` sẽ quyết định cần làm gì:

- Nếu đã có `OAuth2AuthorizedClient` và **Access Token vẫn còn hiệu lực**, trả về ngay.
- Nếu Access Token **đã hết hạn** nhưng còn **Refresh Token**, tự động Refresh Access Token rồi trả về `OAuth2AuthorizedClient` mới.
- Nếu **chưa có `OAuth2AuthorizedClient`**, khởi động Authorization Code Flow (thông qua `AuthorizationCodeOAuth2AuthorizedClientProvider`). Provider sẽ ném `ClientAuthorizationRequiredException`, sau đó `OAuth2AuthorizationRequestRedirectFilter` sẽ bắt exception này và redirect người dùng sang Google để cấp quyền.

Sau khi `OAuth2AuthorizedClientManager` trả về kết quả, `OAuth2AuthorizedClientArgumentResolver` sẽ truyền object đó vào tham số `client` của method Controller.

Nhờ vậy, khi Controller bắt đầu thực thi, nó chỉ đơn giản nhận được một `OAuth2AuthorizedClient` hợp lệ mà **không cần quan tâm Access Token được lấy ở đâu, có cần Refresh hay không, hay người dùng vừa phải đăng nhập Google**.

---

#### Có thể hình dung toàn bộ quá trình như sau

```
Controller chuẩn bị được gọi
        │
        ▼
Spring MVC
        │
        ▼
OAuth2AuthorizedClientArgumentResolver
        │
        ▼
OAuth2AuthorizedClientManager
        │
        ├── Có OAuth2AuthorizedClient?
        │
        ├──────────────┬──────────────────────┐
        │              │                      │
        ▼              ▼                      ▼
 Access Token      Access Token          Chưa có
   còn hạn          hết hạn          AuthorizedClient
        │              │                      │
        ▼              ▼                      ▼
 Trả ngay       Refresh Access Token   Authorization Code Flow
 OAuth2AuthorizedClient      │                 │
                             ▼                 ▼
                    Trả OAuth2AuthorizedClient
```

---

#### Giải thích sơ đồ

Có thể hiểu sơ đồ trên theo thứ tự từ trên xuống như sau:

1. Một request được gửi đến Controller.
2. Trước khi gọi method của Controller, Spring MVC phát hiện tham số được đánh dấu bằng `@RegisteredOAuth2AuthorizedClient`.
3. Spring giao việc tạo tham số này cho `OAuth2AuthorizedClientArgumentResolver`.
4. Resolver không tự tìm Access Token, mà **ủy quyền** cho `OAuth2AuthorizedClientManager`.
5. Manager kiểm tra xem người dùng hiện tại đã có `OAuth2AuthorizedClient` hay chưa:
    - Nếu Access Token vẫn còn hiệu lực thì trả về ngay.
    - Nếu Access Token đã hết hạn nhưng có Refresh Token thì tự động Refresh rồi trả về.
    - Nếu chưa từng có `OAuth2AuthorizedClient` thì khởi động Authorization Code Flow để người dùng đăng nhập Google và cấp quyền.
6. Sau khi nhận được `OAuth2AuthorizedClient`, Resolver truyền object này vào tham số của method Controller.
7. Controller chỉ việc sử dụng `client.getAccessToken()` để gọi Resource Server mà không cần quan tâm phía dưới đã xảy ra những gì.

## 4. Bảng ánh xạ: thành phần ↔ nhiệm vụ ↔ thay cho gì ở Phase 1

| Thành phần (Phase 2) | Nhiệm vụ | Thay cho (Phase 1 - viết tay) |
|----------------------|----------|-------------------------------|
| `ClientRegistrationRepository` | Giữ thông tin client `google` | `GoogleOAuthProperties` |
| Resolver + `withPkce()` | Sinh state + PKCE, ghép authorization request | `PkceUtil` + build URL trong `AuthController` |
| `OAuth2AuthorizationRequestRedirectFilter` | Redirect sang Google | `/oauth2/authorize` trong `AuthController` |
| `OAuth2AuthorizationCodeGrantFilter` | Nhận callback, verify state, đổi token | `/oauth2/callback` + `GoogleOAuthService` |
| `OAuth2AuthorizedClientRepository` | Lưu token theo session | `session.setAttribute(SESSION_TOKEN, ...)` |
| `OAuth2AuthorizedClientManager` (`.refreshToken()`) | Auto refresh token | `TokenService.getValidAccessToken()` |
| `@RegisteredOAuth2AuthorizedClient` | Lấy token cho controller | `tokenService.getValidAccessToken(session)` |

→ Toàn bộ cột phải (7 chỗ viết tay) đã bị xóa ở Phase 2 và thay bằng cấu hình.

## 5. TẦNG 3 — Hoạt động trong từng chức năng của dự án

### 5.1. Chức năng "Connect" — lần đầu, chưa có token

Người dùng bấm nút trên `index.html`:

```html
<a href="/connected"><button>Connect Google Calendar</button></a>
```

Request sẽ được gửi đến Controller:

```java
@GetMapping("/connected")
public String connected(
        @RegisteredOAuth2AuthorizedClient("google") OAuth2AuthorizedClient client,
        Model model) {

    OAuth2AccessToken accessToken = client.getAccessToken();

    model.addAttribute("hasRefreshToken",
            client.getRefreshToken() != null);

    model.addAttribute("expiresAt",
            accessToken.getExpiresAt());

    model.addAttribute("scopes",
            accessToken.getScopes());

    ...
}
```

Điểm đặc biệt của method này là tham số:

```java
@RegisteredOAuth2AuthorizedClient("google")
OAuth2AuthorizedClient client
```

Trước khi Controller được thực thi, Spring MVC sẽ giao việc tạo tham số này cho `OAuth2AuthorizedClientArgumentResolver` (đã trình bày ở mục **3.5**).

Resolver tiếp tục gọi `OAuth2AuthorizedClientManager` để yêu cầu một `OAuth2AuthorizedClient` hợp lệ.

Vì đây là **lần đầu người dùng truy cập**, trong `HttpSession` **chưa có** `OAuth2AuthorizedClient`, nên `OAuth2AuthorizedClientManager` sẽ khởi động **Authorization Code Flow**. Quá trình này sẽ ném `ClientAuthorizationRequiredException`, được `OAuth2AuthorizationRequestRedirectFilter` bắt lại và chuyển hướng trình duyệt sang Google để người dùng đăng nhập và cấp quyền.

Sau khi người dùng hoàn tất việc cấp quyền, Google sẽ redirect trình duyệt quay trở lại ứng dụng. Spring sẽ đổi Authorization Code lấy Access Token, tạo `OAuth2AuthorizedClient` và lưu vào `OAuth2AuthorizedClientRepository` (thực chất là lưu trong `HttpSession` của người dùng).

Đến lúc này, Spring **thực hiện lại request ban đầu** đến `/connected`. Lần này, `OAuth2AuthorizedClientManager` đã tìm thấy `OAuth2AuthorizedClient` trong `HttpSession`, nên `OAuth2AuthorizedClientArgumentResolver` có thể truyền object này vào Controller và method mới thực sự được thực thi.

Do đó, có thể xem cùng một URL `/connected` được xử lý theo **hai giai đoạn**:

- **Lần thứ nhất:** chưa có `OAuth2AuthorizedClient` → khởi động Authorization Code Flow, Controller **chưa được thực thi**.
- **Lần thứ hai:** đã có `OAuth2AuthorizedClient` → Controller được thực thi và có thể sử dụng Access Token để gọi Google Calendar API.

Có thể hình dung như sau:

```
Lần 1

Browser
    │
GET /connected
    │
    ▼
OAuth2AuthorizedClientArgumentResolver
    │
    ▼
OAuth2AuthorizedClientManager
    │
    ▼
Chưa có OAuth2AuthorizedClient
    │
    ▼
Redirect sang Google
```

```
Người dùng đăng nhập + cấp quyền
            │
            ▼
Google callback
            │
            ▼
Đổi Authorization Code
            │
            ▼
Lưu OAuth2AuthorizedClient vào HttpSession
            │
            ▼
Thực hiện lại GET /connected
```

```
Lần 2

Browser
    │
GET /connected
    │
    ▼
OAuth2AuthorizedClientArgumentResolver
    │
    ▼
OAuth2AuthorizedClientManager
    │
    ▼
Đã có OAuth2AuthorizedClient
    │
    ▼
Controller được thực thi
    │
    ▼
client.getAccessToken()
```

---

> **Điểm mấu chốt cần nhớ**

Mặc dù người dùng chỉ **nhấn nút một lần**, nhưng URL `/connected` được xử lý qua **hai lần**:

- **Lần thứ nhất** chỉ nhằm mục đích khởi động Authorization Code Flow, nên Controller **chưa chạy**.
- **Lần thứ hai** diễn ra sau khi Google cấp quyền thành công. Khi đó `OAuth2AuthorizedClient` đã được lưu trong `HttpSession`, nên Controller mới thực sự được thực thi và có thể sử dụng Access Token.

### 5.2. Chức năng xem lịch / sự kiện — sử dụng Access Token để gọi Google API

Sau khi người dùng đã hoàn thành Authorization Code Flow, `OAuth2AuthorizedClient` đã được lưu trong `HttpSession`.

Vì vậy, ở các request tiếp theo, Controller chỉ cần khai báo:

```java
@GetMapping("/calendars")
public String calendars(
        @RegisteredOAuth2AuthorizedClient("google") OAuth2AuthorizedClient client,
        Model model) {

    String accessToken = client.getAccessToken().getTokenValue();

    CalendarListResponse calendars =
            calendarService.listCalendars(accessToken);

    ...
}
```

Trước khi method được thực thi, `OAuth2AuthorizedClientArgumentResolver` sẽ lấy `OAuth2AuthorizedClient` từ `OAuth2AuthorizedClientManager` và truyền vào tham số `client`.

Do đó, Controller chỉ việc lấy Access Token thông qua:

```
String accessToken = client.getAccessToken().getTokenValue();
```

sau đó truyền cho tầng Service để gọi Google Calendar API.

---

> **GoogleCalendarService sử dụng Access Token như thế nào?**

Trong `GoogleCalendarService`, Access Token được gắn vào HTTP Header theo chuẩn **Bearer Token**:

```java
return restClient.get()
        .uri(CALENDAR_LIST_URI)
        .header(HttpHeaders.AUTHORIZATION, "Bearer " + accessToken)
        .retrieve()
        .body(CalendarListResponse.class);
```

Khi gửi request, HTTP Request sẽ có dạng:

```HTTP
GET https://www.googleapis.com/calendar/v3/users/me/calendarList
Authorization: Bearer eyJhbGciOi...
```

Google Resource Server sẽ đọc Access Token từ header `Authorization` để xác thực người dùng, kiểm tra quyền truy cập (`scope`), sau đó mới trả về danh sách Calendar.

---

> **Điều gì xảy ra nếu Access Token đã hết hạn?**

Controller và `GoogleCalendarService` **không cần quan tâm** Access Token còn hạn hay không.

Mỗi khi gặp tham số:

```java
@RegisteredOAuth2AuthorizedClient("google")
OAuth2AuthorizedClient client
```

Spring đều giao việc lấy `OAuth2AuthorizedClient` cho `OAuth2AuthorizedClientManager`.

Manager sẽ tự kiểm tra trạng thái của Access Token:

- Nếu Access Token vẫn còn hiệu lực → sử dụng ngay.
- Nếu Access Token đã hết hạn nhưng có Refresh Token → tự động lấy Access Token mới rồi mới truyền `OAuth2AuthorizedClient` vào Controller.
- Nếu chưa có `OAuth2AuthorizedClient` → khởi động Authorization Code Flow để người dùng đăng nhập Google.

Nhờ đó, khi Controller bắt đầu thực thi, `client.getAccessToken()` luôn là **Access Token hợp lệ**.

---

> Có thể hình dung toàn bộ quá trình như sau

```
Browser
    │
GET /calendars
    │
    ▼
Controller
    │
    ▼
@RegisteredOAuth2AuthorizedClient
    │
    ▼
OAuth2AuthorizedClientArgumentResolver
    │
    ▼
OAuth2AuthorizedClientManager
    │
    ├── Access Token còn hạn
    │         │
    │         ▼
    │   Trả OAuth2AuthorizedClient
    │
    └── Access Token hết hạn
              │
              ▼
      Refresh Access Token
              │
              ▼
      Trả OAuth2AuthorizedClient
              │
              ▼
Controller
    │
client.getAccessToken()
    │
    ▼
GoogleCalendarService
    │
Authorization: Bearer <access_token>
    │
    ▼
Google Calendar API
```

---

> **Điểm mấu chốt cần nhớ**

Điểm quan trọng nhất của cơ chế này là **Controller không trực tiếp quản lý Access Token**. Controller chỉ nhận một `OAuth2AuthorizedClient` đã được Spring chuẩn bị sẵn và sử dụng:

```
client.getAccessToken()
```

để gọi Google API.

Toàn bộ việc:

- lấy `OAuth2AuthorizedClient` từ `HttpSession`,
- kiểm tra Access Token còn hạn hay không,
- tự động Refresh Access Token khi cần,
- hoặc khởi động Authorization Code Flow nếu chưa có token,

đều được Spring Security xử lý phía sau thông qua `OAuth2AuthorizedClientArgumentResolver` và `OAuth2AuthorizedClientManager`.

### 5.3. Chức năng auto-refresh — Access Token hết hạn

Access Token do Google cấp chỉ có thời gian sống khoảng **1 giờ**. Sau khi hết hạn, người dùng vẫn có thể tiếp tục sử dụng ứng dụng mà **không cần đăng nhập hay cấp quyền lại**.

Ví dụ, người dùng truy cập:

```HTTP
GET /calendars
```

Controller vẫn giữ nguyên:

```java
@GetMapping("/calendars")
public String calendars(
        @RegisteredOAuth2AuthorizedClient("google")
        OAuth2AuthorizedClient client,
        Model model) {

    String accessToken = client.getAccessToken().getTokenValue();

    CalendarListResponse calendars =
            calendarService.listCalendars(accessToken);

    ...
}
```

Điểm khác biệt là **trước khi Controller được thực thi**, `OAuth2AuthorizedClientArgumentResolver` sẽ tiếp tục yêu cầu `OAuth2AuthorizedClientManager` cung cấp một `OAuth2AuthorizedClient` hợp lệ.

Lần này, Manager phát hiện:

- đã có `OAuth2AuthorizedClient` trong `HttpSession`;
- nhưng **Access Token đã hết hạn**;
- và vẫn còn **Refresh Token**.

Do đã cấu hình:

```java
OAuth2AuthorizedClientProvider provider =
        OAuth2AuthorizedClientProviderBuilder.builder()
                .authorizationCode()
                .refreshToken()
                .build();
```

nên `OAuth2AuthorizedClientManager` sẽ giao việc cho `RefreshTokenOAuth2AuthorizedClientProvider`.

Provider này tự động gửi request đến **Token Endpoint** của Google với:

- `grant_type=refresh_token`
- `refresh_token`
- `client_id`
- `client_secret` (nếu cần)

để đổi lấy **Access Token mới**.

Sau khi nhận được Access Token mới, Spring sẽ cập nhật lại `OAuth2AuthorizedClient` trong `OAuth2AuthorizedClientRepository` (thực chất là cập nhật object trong `HttpSession`), rồi mới trả `OAuth2AuthorizedClient` cho Controller.

Vì vậy, khi Controller bắt đầu thực thi:

```java
String accessToken = client.getAccessToken().getTokenValue();
```

thì `accessToken` đã là **Access Token mới**, hoàn toàn hợp lệ để gọi Google Calendar API.

> **Có thể hình dung toàn bộ quá trình như sau**

```

      │
      ▼
OAuth2AuthorizedClientArgumentResolver
      │
      ▼
OAuth2AuthorizedClientManager
      │
      ▼
Đọc OAuth2AuthorizedClient từ HttpSession
      │
      ▼
Access Token hết hạn?
      │
      ├── Không
      │      │
      │      ▼
      │  Trả OAuth2AuthorizedClient
      │
      └── Có
             │
             ▼
RefreshTokenOAuth2AuthorizedClientProvider
             │
             ▼
POST /token
(grant_type=refresh_token)
             │
             ▼
Google Token Endpoint
             │
             ▼
Access Token mới
             │
             ▼
Cập nhật OAuth2AuthorizedClient
trong HttpSession
             │
             ▼
Trả OAuth2AuthorizedClient
             │
             ▼
Controller
             │
             ▼
Google Calendar API
```

---

> **Điểm mấu chốt cần nhớ**

Điều quan trọng là **Controller hoàn toàn không biết** Access Token đã từng hết hạn.

Khi Controller nhận được:

```java
@RegisteredOAuth2AuthorizedClient
OAuth2AuthorizedClient client
```

thì Spring Security đã đảm bảo `client` luôn chứa **Access Token còn hiệu lực**.

Toàn bộ quá trình:

- kiểm tra thời hạn của Access Token,
- sử dụng Refresh Token để lấy Access Token mới,
- cập nhật lại `OAuth2AuthorizedClient` trong `HttpSession`,

đều được Spring Security thực hiện tự động trước khi Controller bắt đầu chạy.

Đây chính là ý nghĩa của **auto-refresh** hay **refresh trong suốt (transparent refresh)**: người dùng vẫn sử dụng ứng dụng bình thường, không cần đăng nhập hay cấp quyền lại, còn Controller cũng không phải viết bất kỳ đoạn mã nào để kiểm tra hoặc refresh Access Token.
### 5.4. `state` và PKCE bảo vệ điều gì (nhắc lại nhanh)

- **`state`**: Spring tự sinh, lưu trong session, đối chiếu ở callback (mục 3.3b) → chống **CSRF / callback giả mạo**.
- **PKCE** (`code_verifier`/`code_challenge`): kẻ tấn công dù cướp được `code` cũng **không đổi được token** vì không biết `code_verifier` → chống **đánh cắp authorization code**.

Hai cơ chế này ở Phase 1 ta tự làm trong `PkceUtil` + `AuthController`; ở Phase 2 do resolver (mục 2.3) và filter (mục 3.3) lo, ta chỉ "bật công tắc" `withPkce()`.

## 6. Tóm tắt một câu cho mỗi thành phần

- `permitAll()` → không chặn URL; để việc xin quyền kích hoạt đúng lúc cần token.
- `oauth2Client()` → bật chế độ "xin quyền gọi API", không tạo login.
- `authorizationRequestResolver` + `withPkce()` + `offline/consent` → tùy biến request gửi Google (thêm PKCE và xin refresh token).
- `OAuth2AuthorizedClientManager` + `.refreshToken()` → auto lấy/refresh token cho controller.
- **Phần ẩn** (`ClientRegistrationRepository`, 2 filter, 2 endpoint, `AuthorizedClientRepository`, argument resolver) → Spring tự dựng; config của ta chỉ cắm vào và tinh chỉnh.

> Hiểu đúng `SecurityConfig` = hiểu rằng **ta đang cấu hình một cỗ máy có sẵn**, chứ không tự viết cỗ máy đó. Ngắn là vì phần lớn đã được Spring làm sẵn bên dưới.
