# Luồng Authorize — Khởi tạo Authorization Request

Đây là **bước mở màn** của Authorization Code Grant. Mục tiêu: chuẩn bị các tham số an toàn (`state`, `PKCE`) rồi **redirect** trình duyệt sang trang consent của Google để người dùng cấp quyền.

Endpoint phụ trách: `GET /oauth2/authorize` trong `AuthController`.

---

## Vị trí trong toàn bộ flow

```
[/oauth2/authorize]   <-- doc nay mo ta buoc nay
        │
        ▼
   Google consent
        │
        ▼
[/oauth2/callback]    <-- doc #3
        │
        ▼
   Calendar API        <-- doc #4
```

Trong bước này **chưa có token nào cả**. Ta mới chỉ *xin phép* — nói với Google "tôi là client X, muốn quyền Y, hãy hỏi người dùng và gửi authorization code về đúng địa chỉ Z".

---

## Toàn cảnh sơ đồ

```
Browser
   │
   │  GET /oauth2/authorize
   ▼
AuthController.authorize()
   │
   ├── 1. Sinh state ngẫu nhiên                     (chống CSRF)
   ├── 2. Sinh code_verifier + code_challenge (S256) (PKCE)
   │
   ├── 3. Lưu vào HttpSession (phía server):
   │        oauth_state         = state
   │        oauth_code_verifier = code_verifier
   │
   ├── 4. Build URL authorize, gửi kèm:
   │        client_id, redirect_uri, response_type=code,
   │        scope, state, code_challenge, S256,
   │        access_type=offline, prompt=consent
   │
   └── 5. HTTP 302 Redirect
   ▼
https://accounts.google.com/o/oauth2/v2/auth?...
   │
   │  Người dùng đăng nhập + bấm "Allow"
   ▼
Google redirect về /oauth2/callback?code=...&state=...
```

Điểm mấu chốt cần nhớ ngay: **`code_verifier` và `state` được giữ lại trong session ở server, KHÔNG gửi cho Google.** Google chỉ nhận `code_challenge` (bản băm) và `state`. Đây là nền tảng của toàn bộ tính an toàn.

---

## Chi tiết từng bước (kèm code trong dự án)

### Bước 1 & 2 — Sinh `state` và `PKCE`

```java
// AuthController.authorize()
String state = PkceUtil.generateState();
String codeVerifier = PkceUtil.generateCodeVerifier();
String codeChallenge = PkceUtil.generateCodeChallenge(codeVerifier);
```

Cả 3 giá trị đều sinh từ `SecureRandom` (ngẫu nhiên, khó đoán). Xem `PkceUtil`:

```java
public final class PkceUtil {

    private static final SecureRandom SECURE_RANDOM = new SecureRandom();
    private static final Base64.Encoder URL_ENCODER = Base64.getUrlEncoder().withoutPadding();

    // code_verifier: 32 byte ngau nhien -> base64url (~43 ky tu)
    public static String generateCodeVerifier() {
        byte[] bytes = new byte[32];
        SECURE_RANDOM.nextBytes(bytes);
        return URL_ENCODER.encodeToString(bytes);
    }

    // code_challenge = BASE64URL( SHA-256( code_verifier ) )
    public static String generateCodeChallenge(String codeVerifier) {
        MessageDigest digest = MessageDigest.getInstance("SHA-256");
        byte[] hash = digest.digest(codeVerifier.getBytes(StandardCharsets.US_ASCII));
        return URL_ENCODER.encodeToString(hash);
    }

    // state: 16 byte ngau nhien -> base64url
    public static String generateState() {
        byte[] bytes = new byte[16];
        SECURE_RANDOM.nextBytes(bytes);
        return URL_ENCODER.encodeToString(bytes);
    }
}
```

Quan hệ giữa `code_verifier` và `code_challenge`:

```
code_verifier  =  "aoTBnDw1N66Cl..."          (bí mật, giữ ở server)
                        │
                        │  SHA-256  +  Base64URL
                        ▼
code_challenge =  "HmhhUzBTdkNa..."            (công khai, gửi cho Google)
```

Từ `code_challenge` **không thể suy ngược** ra `code_verifier` (vì SHA-256 là hàm một chiều). Đó là lý do gửi challenge đi thì an toàn.

### Bước 3 — Lưu `state` và `code_verifier` vào session

```java
session.setAttribute(SESSION_STATE, state);
session.setAttribute(SESSION_CODE_VERIFIER, codeVerifier);
```

với các hằng số key:

```java
public static final String SESSION_STATE = "oauth_state";
public static final String SESSION_CODE_VERIFIER = "oauth_code_verifier";
```

Vì sao phải lưu?
- `state`: để bước callback **so lại** — nếu state trả về không khớp thì đây là request giả mạo/CSRF.
- `code_verifier`: để bước callback dùng nó **chứng minh** với Google rằng chính client này đã khởi tạo request (PKCE).

Nhờ cơ chế session (xem doc #1), mỗi trình duyệt có `oauth_state` / `oauth_code_verifier` **riêng**, không lẫn giữa những người dùng khác nhau.

### Bước 4 — Build Authorization Request URL

```java
String authorizeUrl = UriComponentsBuilder
        .fromUriString(props.authorizationUri())   // https://accounts.google.com/o/oauth2/v2/auth
        .queryParam("client_id", props.clientId())
        .queryParam("redirect_uri", props.redirectUri())
        .queryParam("response_type", "code")           // xin authorization CODE
        .queryParam("scope", props.scope())
        .queryParam("state", state)                    // chống CSRF
        .queryParam("code_challenge", codeChallenge)   // PKCE (chỉ gửi challenge)
        .queryParam("code_challenge_method", "S256")
        .queryParam("access_type", "offline")          // xin cả REFRESH token
        .queryParam("prompt", "consent")               // luôn hiện consent -> chắc chắn có refresh token
        .build()
        .encode()   // encode đúng cách (scope có ':' và '/')
        .toUriString();
```

Ý nghĩa từng tham số:

| Tham số | Vai trò |
|---------|---------|
| `client_id` | App nào đang xin quyền |
| `redirect_uri` | Google **chỉ** trả code về đúng URI đã đăng ký trước → chống chiếm đoạt code |
| `response_type=code` | Chọn luồng Authorization Code (không lấy token trực tiếp trên URL) |
| `scope` | Xin quyền gì — ở đây `calendar.readonly` |
| `state` | Chuỗi ngẫu nhiên; callback phải trả đúng chuỗi này → chống CSRF |
| `code_challenge` + `code_challenge_method=S256` | Bản băm của `code_verifier` → PKCE |
| `access_type=offline` | Cho phép cấp **refresh token** |
| `prompt=consent` | Ép hiện lại màn consent để chắc chắn nhận refresh token |

> `.encode()` là bắt buộc: `scope` chứa `:` và `/` (ví dụ `https://www.googleapis.com/auth/calendar.readonly`), phải được encode đúng khi đưa vào query string.

### Bước 5 — Redirect sang Google

```java
return "redirect:" + authorizeUrl;
```

Spring trả về **HTTP 302** kèm header `Location: https://accounts.google.com/...`. Trình duyệt tự động đi tới trang consent của Google.

## Ai giữ gì sau bước này?

```
                 ┌─────────────────────────────┐
   SERVER (session)                              GOOGLE nhận được (trên URL)
   ┌──────────────────────────┐                 ┌──────────────────────────┐
   │ oauth_state         = S  │  ──── state ──▶ │ state         = S        │
   │ oauth_code_verifier = V  │                 │ code_challenge = SHA256(V)│
   └──────────────────────────┘   ─ challenge ▶ │ client_id, scope, ...     │
        (V KHÔNG bao giờ rời server)            └──────────────────────────┘
```

- Server giữ **bí mật** `code_verifier (V)` trong session.
- Google chỉ thấy `code_challenge` = băm của V, và `state`.

---

## Hai lớp bảo vệ khác nhau (không thay thế nhau)

`state` và `PKCE` giải quyết **hai vấn đề hoàn toàn khác nhau**. Dưới đây là cơ chế chi tiết của từng cái.

---

### A. `state` chống CSRF ở bước callback như thế nào?

**CSRF trong OAuth (authorization code injection) là gì?**

Callback `/oauth2/callback?code=...` chỉ là một request GET bình thường. Nếu **không có gì ràng buộc**, thì bất kỳ ai cũng có thể lừa trình duyệt nạn nhân gọi callback với **một authorization code do kẻ tấn công chuẩn bị sẵn**.

Kịch bản tấn công khi KHÔNG có `state`:

```
1. Kẻ tấn công tự bấm "Connect" bằng tài khoản Google CỦA HẮN
   -> Google cấp cho hắn 1 authorization code:  code_ATTACKER
   -> Nhưng hắn KHÔNG dùng code này để hoàn tất

2. Hắn nhúng vào web/email 1 link (hoặc ảnh tự động load):
      http://localhost:8080/oauth2/callback?code=code_ATTACKER

3. Nạn nhân (đang đăng nhập app) vô tình mở link đó
   -> Trình duyệt nạn nhân gọi callback với code_ATTACKER
   -> App đổi code_ATTACKER lấy token -> lưu vào SESSION CỦA NẠN NHÂN

4. Hậu quả: session của nạn nhân giờ gắn với tài khoản Google của kẻ tấn công.
   Nạn nhân tưởng đang thao tác trên tài khoản mình, nhưng thực chất
   mọi dữ liệu (sự kiện tạo ra, thông tin nhập...) đổ vào tài khoản kẻ tấn công.
```

**`state` chặn điều này ra sao?**

Ở bước authorize, ta sinh `state` ngẫu nhiên và **gắn nó vào session của nạn nhân**:

```java
// authorize()
String state = PkceUtil.generateState();
session.setAttribute(SESSION_STATE, state);   // state buộc chặt vào session người khởi tạo
// ... state cũng được gửi lên Google qua query param
```

Ở bước callback, ta **so lại**:

```java
// callback()
String savedState = (String) session.getAttribute(SESSION_STATE);
if (savedState == null || !savedState.equals(state)) {
    model.addAttribute("error", "State không khớp -> Nghi ngờ CSRF. Từ chối");
    return "error-page";
}
```

Vì sao kẻ tấn công thua:

```
Session nạn nhân giữ:   oauth_state = S_victim   (ngẫu nhiên, kẻ tấn công KHÔNG biết)

Link giả của kẻ tấn công:  /oauth2/callback?code=code_ATTACKER&state=???
                                                                      │
                     kẻ tấn công không đoán được S_victim ────────────┘

callback so:  state trên URL  ==  oauth_state trong session ?
              ───────────────────────────────────────────────
                        KHÔNG KHỚP  ->  từ chối
```

- `state` sinh từ `SecureRandom`, **khác nhau cho mỗi phiên**, và **lưu phía server** (không nằm trên URL cố định) → kẻ tấn công không thể biết `S_victim` để nhét vào link giả.
- Google, khi redirect thật, **trả lại đúng** `state` mà app đã gửi đi. Nên callback hợp lệ luôn khớp; callback giả mạo thì không.

> Bản chất: `state` **buộc chặt callback vào đúng phiên đã khởi tạo authorize**. Trả lời câu hỏi *"cái callback này có thực sự do chính người dùng này bắt đầu không?"*.

---

### B. `PKCE` chống đánh cắp authorization code như thế nào?

**Authorization code bị đánh cắp bằng cách nào?**

`code` được Google trả về **trên URL** của callback:

```
http://localhost:8080/oauth2/callback?code=4/0AeanS0b...&state=...
```

URL thì dễ rò rỉ qua nhiều đường:
- Lịch sử trình duyệt, log của server/proxy.
- Header `Referer` gửi sang bên thứ ba.
- Trên mobile: app độc hại đăng ký trùng custom-scheme redirect và "cướp" code.

Nếu **không có PKCE**, kẻ tấn công cướp được `code` có thể tự gọi token endpoint để đổi lấy token:

```
POST /token
   grant_type=authorization_code
   code=<code đánh cắp được>
   redirect_uri=...
   client_id=...
-> LẤY ĐƯỢC access token   (nguy hiểm!)
```

**PKCE chặn điều này ra sao?**

Nhớ lại: ở bước authorize, ta chỉ gửi cho Google **`code_challenge`** (= băm SHA-256 của `code_verifier`), còn **`code_verifier` giữ bí mật trong session**:

```java
// authorize()
String codeVerifier  = PkceUtil.generateCodeVerifier();          // bí mật, lưu session
String codeChallenge = PkceUtil.generateCodeChallenge(codeVerifier); // gửi cho Google
session.setAttribute(SESSION_CODE_VERIFIER, codeVerifier);
// URL gửi Google: ...&code_challenge=<challenge>&code_challenge_method=S256
```

Google **ghi nhớ** `code_challenge` gắn với `code` mà nó phát ra. Đến bước đổi token (doc #3), token endpoint **bắt buộc** kèm `code_verifier` gốc:

```java
// GoogleOAuthService.exchangeCodeForToken()
form.add("grant_type", "authorization_code");
form.add("code", code);
form.add("code_verifier", codeVerifier);   // <-- xuất trình bí mật gốc
```

Google tự tính `SHA-256(code_verifier)` và so với `code_challenge` đã lưu:

```
Lúc authorize:   Google lưu   challenge = SHA256(V)
Lúc đổi token:   client gửi   code + code_verifier = V'
                 Google kiểm:  SHA256(V')  ==  challenge ?

   Client thật:      V' = V   ->  SHA256(V) == SHA256(V)   ->  OK, cấp token
   Kẻ tấn công:      chỉ có code, KHÔNG có V
                     đoán V từ challenge? -> bất khả thi (SHA-256 một chiều)
                     -> thiếu code_verifier -> Google từ chối (invalid_grant)
```

Vì sao kẻ tấn công thua:
- Thứ đi kèm token request là `code_verifier` (bí mật), **không phải** `code_challenge` (thứ có thể lộ trên URL authorize).
- Từ `code_challenge` **không suy ngược** ra `code_verifier` được (SHA-256 là hàm một chiều).
- `code_verifier` **chỉ tồn tại trong session của client hợp lệ**, không bao giờ xuất hiện trên đường truyền tới khi đổi token (mà bước đổi token là server-to-server, kín).

> Bản chất: PKCE **buộc chặt authorization code vào đúng client đã tạo ra nó**. Trả lời câu hỏi *"kẻ đang cầm code này có đúng là client đã khởi tạo request ban đầu không?"*. Có `code` mà không có `code_verifier` thì `code` trở nên vô dụng.

> Ghi chú: dự án là web app *confidential* (có `client_secret`), bản thân secret đã là một lớp bảo vệ. Nhưng theo OAuth 2.1, PKCE được khuyến nghị cho **mọi** client như một lớp phòng thủ theo chiều sâu — nên ta vẫn dùng.

---

### Tóm tắt sự khác biệt

```
                state  ──►  bảo vệ "ai GỬI callback về"       (chống CSRF / code injection)
                PKCE   ──►  bảo vệ "ai được ĐỔI code lấy token" (chống đánh cắp code)
```

| | `state` | `PKCE` |
|---|---------|--------|
| Chống | CSRF / authorization code injection | Đánh cắp / tái sử dụng authorization code |
| Ràng buộc code vào | đúng **phiên (session)** đã khởi tạo | đúng **client** đã khởi tạo |
| Bí mật nằm ở | `oauth_state` trong session | `code_verifier` trong session |
| Kiểm tra tại | callback của **app** (so state) | token endpoint của **Google** (so challenge) |

Hai mục tiêu khác nhau ⇒ **dùng đồng thời cả hai**, không cái nào thay được cái nào.

## Cấu hình liên quan (application.properties)

```properties
google.oauth.client-id=${GOOGLE_CLIENT_ID}
google.oauth.client-secret=${GOOGLE_CLIENT_SECRET}
google.oauth.redirect-uri=http://localhost:8080/oauth2/callback
google.oauth.scope=https://www.googleapis.com/auth/calendar.readonly
google.oauth.authorization-uri=https://accounts.google.com/o/oauth2/v2/auth
google.oauth.token-uri=https://oauth2.googleapis.com/token
```

Các giá trị này được nạp vào `GoogleOAuthProperties` (record `@ConfigurationProperties(prefix = "google.oauth")`) và inject vào `AuthController` qua `props`.

## Tóm tắt

1. `authorize()` sinh `state` + cặp PKCE (`code_verifier` bí mật, `code_challenge` công khai).
2. Lưu `state` và `code_verifier` vào **session server** (mỗi browser một bản riêng).
3. Build URL với đầy đủ tham số an toàn, chỉ gửi `code_challenge` (không gửi verifier).
4. Redirect 302 sang Google để người dùng consent.
5. Kết thúc bước này chưa có token — Google sẽ gọi lại `/oauth2/callback` với `code` + `state` (xem doc #3).
