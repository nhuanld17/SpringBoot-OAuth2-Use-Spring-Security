# 📚 AUTHORIZATION GRANT TYPES TRONG OAUTH 2.0

---

## ✅ CHECKLIST NỘI DUNG BÀI HỌC

- **Grant Type là gì** và tại sao cần nhiều loại khác nhau
- **Authorization Code Grant** - Flow phổ biến nhất cho web apps
- **Password Grant (Resource Owner Password Credentials)** - Khi nào nên/không nên dùng
- **Client Credentials Grant** - Backend-to-backend authentication
- **Refresh Token Grant** - Làm mới access token mà không cần đăng nhập lại
- So sánh và lựa chọn grant type phù hợp cho từng tình huống

---

## 🎯 PHẦN 1: GRANT TYPE LÀ GÌ?

### Khái niệm cốt lõi

**[CONFIDENT]** - Grant Type (kiểu cấp phép) là **cách thức mà một ứng dụng (client) có thể lấy được access token** từ Authorization Server. Hiểu đơn giản, nó là "quy trình" để client chứng minh được quyền truy cập tài nguyên của user.

> **Ví dụ thực tế**: Giống như bạn có nhiều cách để vào nhà - dùng chìa khóa (Authorization Code), nhập mật khẩu cửa (Password Grant), hoặc quẹt thẻ từ (Client Credentials). Mỗi cách phù hợp với tình huống khác nhau!

OAuth 2.0 định nghĩa **5 grant types chính**:
1. **Authorization Code** - Phổ biến nhất, an toàn nhất
2. **Implicit** - ⚠️ Đã deprecated trong OAuth 2.1[](https://oauth.net/2/grant-types/implicit/)
3. **Resource Owner Password Credentials** - ⚠️ Đã deprecated trong OAuth 2.1[](https://www.descope.com/blog/post/oauth-2-0-vs-oauth-2-1)
4. **Client Credentials** - Cho machine-to-machine authentication

**Lưu ý quan trọng**: Implicit Grant đã bị loại bỏ trong OAuth 2.1 do vấn đề bảo mật, nên tài liệu này không đề cập đến nó.

#### Cơ chế bổ sung: Refresh Token

**[CONFIDENT]** - **Refresh Token KHÔNG phải là một grant type**, mà là cơ chế để:[](https://oauth.net/2/grant-types/refresh-token/)

- Lấy **access token mới** khi token cũ hết hạn
- Sử dụng **KẾT HỢP** với Authorization Code hoặc Password Grant
- Cho phép user duy trì session mà không cần đăng nhập lại

## 🔐 PHẦN 2: AUTHORIZATION CODE GRANT

### Tổng quan

**[CONFIDENT]** - Đây là **grant type được khuyên dùng nhất** cho web và mobile apps. Authorization Code Grant cho phép user cấp quyền cho client mà **KHÔNG cần chia sẻ mật khẩu** với client.

### Nguyên lý hoạt động

```
┌─────────┐                                     ┌──────────────────┐
│  User   │                                     │ Authorization    │
│(Browser)│                                     │    Server        │
└────┬────┘                                     └────────┬─────────┘
     │                                                   │
     │  1. Nhấn "Login with Google"                      │
     │     Client redirect user đến /authorize           │
     ├──────────────────────────────────────────────────>│
     │                                                   │
     │  2. User nhập username/password TRỰC TIẾP         │
     │     trên trang của Authorization Server           │
     ├──────────────────────────────────────────────────>│
     │                                                   │
     │  3. ⭐ BƯỚC MỚI: Auth Server hỏi user:            │
     │     "App X muốn truy cập dữ liệu của bạn.         │
     │      Bạn có đồng ý không?"                        │
     │     User nhấn "Đồng ý" (CONSENT)                  │
     ├──────────────────────────────────────────────────>│
     │                                                   │
     │  4. Auth Server trả về AUTHORIZATION CODE         │
     │     (qua redirect URI)                            │
     │<──────────────────────────────────────────────────┤
     │                                                   │
┌────▼────┐                                              │
│ Client  │  5. Client dùng code + client_secret         │
│  App    │     (hoặc code_verifier nếu dùng PKCE)       │
│         │     để đổi lấy ACCESS TOKEN                  │
└────┬────┘ ──────────────────────────────────────────>  │
     │                                                   │
     │  6. Nhận ACCESS TOKEN + REFRESH TOKEN (optional)  │
     │<──────────────────────────────────────────────────┤
     │                                                   │
┌────▼────┐                                     ┌────────▼─────────┐
│ Client  │  7. Dùng access token để gọi API    │  Resource        │
│  App    │ ──────────────────────────────────> │   Server         │
└─────────┘                                     └──────────────────┘
```

### Chi tiết từng bước

#### BƯỚC 1: AUTHORIZATION REQUEST (Yêu cầu cấp quyền)

Client redirect user đến Authorization Server với các tham số:

```http
GET /oauth2/authorize?
  response_type=code          ← Yêu cầu trả về authorization code
  &client_id=abc123          ← ID của ứng dụng client
  &redirect_uri=https://myapp.com/callback  ← Nơi nhận code
  &scope=read write          ← Quyền truy cập yêu cầu
  &state=xyz789              ← CSRF protection + maintain state
  &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM  ← PKCE (nếu dùng)
  &code_challenge_method=S256  ← SHA256 (nếu dùng PKCE)
```

**📝 Lưu ý về tham số `state`**:[](https://oauth.net/2/grant-types/)​

- **Mục đích chính**: Chống tấn công CSRF (Cross-Site Request Forgery)

- **Mục đích phụ**: Duy trì trạng thái ứng dụng giữa lúc yêu cầu cấp quyền và callback

- **Bắt buộc**: Được KHUYẾN NGHỊ trong RFC 6749, NÊN dùng trong OAuth 2.0 Security Best Practice

#### BƯỚC 2: USER AUTHENTICATION (Xác thực người dùng)

- User nhập username/password **TRỰC TIẾP** trên trang Authorization Server
- ⭐ **Điểm quan trọng**: Client app **KHÔNG BAO GIỜ** thấy mật khẩu của user!
- Authorization Server tự do chọn cách xác thực (password, sinh trắc học, MFA...)

#### BƯỚC 3: USER AUTHORIZATION (CONSENT)

**[CONFIDENT]** - Theo RFC 6749 Section 4.1.1:[](https://oauth.net/2/grant-types/)​

> "Authorization Server xác thực người dùng và thiết lập xem người dùng có đồng ý hay từ chối yêu cầu truy cập của client."

Sau khi xác thực thành công, Authorization Server:

1. Hiển thị **màn hình đồng ý** (consent screen) cho user

2. Cho user biết **client nào** đang yêu cầu quyền **gì** (scope)

3. User nhấn "Cho phép" hoặc "Từ chối"

**Ví dụ màn hình đồng ý thực tế (Google)**:

```
┌──────────────────────────────────────┐
│ FitTracker muốn truy cập:            │
│ ✓ Xem hồ sơ Google của bạn           │
│ ✓ Đọc dữ liệu Google Fit của bạn     │
│                                      │
│  [ Hủy bỏ ]        [ Cho phép ]      │
└──────────────────────────────────────┘
```

**Quan trọng**: Nếu user nhấn "Từ chối", Authorization Server trả về lỗi thay vì code.[](https://oauth.net/2/grant-types/)

#### BƯỚC 4: AUTHORIZATION CODE RESPONSE (Trả về mã cấp quyền)

**[CONFIDENT]** - Authorization Server redirect về client với code (RFC 6749 Section 4.1.2):

```http
HTTP/1.1 302 Found
Location: https://myapp.com/callback?
  code=SplxlOBeZQQYbYS6WxSbIA    ← Authorization code (dùng 1 lần, hết hạn sau ~10 phút)
  &state=xyz789                  ← State để xác minh CSRF
```

**⚠️ Đặc điểm của authorization code**:[](https://oauth.net/2/grant-types/)​

- **Thời gian sống ngắn**: Thường hết hạn sau 10 phút
- **Dùng một lần**: Chỉ được sử dụng 1 lần duy nhất
- **Gắn với client**: Chỉ client đã yêu cầu mới đổi được

#### BƯỚC 4: TOKEN REQUEST (Yêu cầu lấy token)

**[CONFIDENT]** - Client đổi code lấy access token (RFC 6749 Section 4.1.3):

**Không dùng PKCE** (confidential client - client bảo mật):

```http
POST /oauth2/token
Host: authorization-server.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Base64(client_id:client_secret)

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https://myapp.com/callback
```

**Dùng PKCE** (public client hoặc confidential client muốn bảo mật cao hơn):

```http
POST /oauth2/token
Host: authorization-server.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https://myapp.com/callback
&client_id=abc123
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk  ← PKCE verifier
```

#### BƯỚC 6: TOKEN RESPONSE (Nhận token)

```json
{
  "access_token": "eyJhbGci...adQssw5c",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA",
  "scope": "read write"
}
```

## Ví dụ thực tế dễ hiểu

**[CONFIDENT]** - Tình huống: Bạn dùng app "FitTracker" và muốn nó đọc dữ liệu sức khỏe từ Google Fit.

1. **Bạn nhấn "Connect Google Fit"** → FitTracker redirect bạn đến `https://accounts.google.com/o/oauth2/v2/auth?...`

2. **Bạn đăng nhập Google** (Google thấy mật khẩu, FitTracker KHÔNG thấy)

3. **⭐ Google hỏi**: "FitTracker muốn đọc dữ liệu Google Fit của bạn. Bạn đồng ý?"

4. **Bạn nhấn "Đồng ý"** → Google redirect bạn về `https://fittracker.com/callback?code=ABC123...`

5. **FitTracker (backend) gửi code + client_secret** đến Google

6. **Google xác minh** và trả về access_token

7. **FitTracker dùng access_token** để gọi Google Fit API

### Cấu hình trong Spring Security

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          google:
            client-id: your-client-id.apps.googleusercontent.com
            client-secret: your-client-secret
            authorization-grant-type: authorization_code
            redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"
            scope: 
              - https://www.googleapis.com/auth/fitness.activity.read
              - profile
              - email
        provider:
          google:
            authorization-uri: https://accounts.google.com/o/oauth2/v2/auth
            token-uri: https://oauth2.googleapis.com/token
            user-info-uri: https://www.googleapis.com/oauth2/v3/userinfo
```

**💡 Spring Security tự động xử lý**:

- PKCE (nếu client là public)
- Tạo và xác thực state parameter
- Bảo vệ CSRF
- Lưu trữ token

## Tại sao cần 2 bước (code → token)?

**[CONFIDENT]** - Đây là câu hỏi nhiều người thắc mắc! Lý do được nêu rõ trong RFC 6749 Section 1.3.1:[](https://www.oauth.com/oauth2-servers/server-side-apps/authorization-code/)

**Lý do bảo mật**:

1. **Xác thực client hai lớp**:[](https://oauth.net/2/grant-types/)​

    - Bước 1: Chứng minh client có quyền redirect user (danh sách redirect_uri hợp lệ)

    - Bước 2: Chứng minh client có `client_secret` (hoặc `code_verifier`)

2. **Tách riêng kênh truyền**:[](https://www.oauth.com/oauth2-servers/server-side-apps/authorization-code/)​

    - **Front-channel** (Trình duyệt): Chỉ truyền authorization code (ít nhạy cảm, sống ngắn, dùng 1 lần)

    - **Back-channel** (Server-to-server): Truyền access token (nhạy cảm, sống lâu)

3. **Access token không bao giờ đi qua trình duyệt**:[](https://oauth.net/2/grant-types/)​

    - Trình duyệt có thể bị tấn công (XSS, lịch sử duyệt web, referrer headers)

    - Access token chỉ backend của client thấy


**So sánh dễ hiểu**:

- **Authorization code** = Phiếu xếp hàng (chỉ để đổi món, hết hạn nhanh, kẻ khác lấy được cũng vô dụng vì thiếu CMND)

- **Client_secret/code_verifier** = CMND (chứng minh bạn là người được nhận)

- **Access token** = Món hàng thật (giá trị cao, cần bảo vệ kỹ)

### Lưu ý

> Web app không có backend thì là public client
> Web app có backend:
> - Nếu **FRONTEND** (React/Vue) làm OAuth → Frontend vẫn là **PUBLIC CLIENT**
> - Nếu **BACKEND** (server) làm OAuth → Backend là **CONFIDENTIAL CLIENT**
### Tăng cường bảo mật với PKCE

**[CONFIDENT]** - PKCE (Proof Key for Code Exchange) giải quyết vấn đề: **Tấn công chặn mã cấp quyền (Authorization Code Interception Attack)** trên public clients.

#### Vấn đề PKCE giải quyết

**Tình huống tấn công** (đặc biệt phổ biến trên mobile apps):

```
1. User đăng nhập thành công
   ↓
2. Authorization Server redirect về app:
   myapp://callback?code=ABC123
   ↓
3. ❌ Ứng dụng độc hại trên cùng thiết bị đã đăng ký 
      cùng URL scheme (URL scheme hijacking)
   ↓
4. ❌ Ứng dụng độc hại CHẶN được authorization code
   ↓
5. ❌ Vì public client KHÔNG CÓ client_secret,
      ứng dụng độc hại có thể dùng code để lấy token!
```

#### **PKCE giải quyết như thế nào?**

Client phải chứng minh nó là client đã tạo authorization request ban đầu bằng `code_verifier` (chỉ client thật mới có).

#### Cách PKCE hoạt động

```
Client tạo (TRƯỚC KHI redirect user):
  code_verifier = chuỗi ngẫu nhiên 43-128 ký tự
    VD: "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
  
  code_challenge = BASE64URL(SHA256(code_verifier))
    VD: "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"

─────────────────────────────────────────────────────────

Bước 1: Authorization Request
  → Client gửi code_challenge đến Authorization Server
  → Auth Server LƯU code_challenge cùng với authorization code
  
Bước 2: Token Request
  → Client gửi code_verifier (plain text)
  → Auth Server verify: 
      BASE64URL(SHA256(code_verifier)) == code_challenge đã lưu
  
  ✅ Nếu khớp → Cấp token (đây là client thật)
  ❌ Nếu không khớp → Từ chối (client giả mạo)
```

**Tại sao ứng dụng độc hại không dùng được code bị chặn?**

- Ứng dụng độc hại chỉ chặn được `code` trong URL callback

- **KHÔNG CÓ** `code_verifier` (chỉ tồn tại trong memory của app thật)

- Khi gửi code đến token endpoint → thiếu `code_verifier` → **BỊ TỪ CHỐI**!

#### Ví dụ code thực tế

#### Bước 1: Tạo PKCE parameters

```javascript
// Tạo code_verifier (43-128 ký tự random)
function generateCodeVerifier() {
  const array = new Uint8Array(32);
  crypto.getRandomValues(array);
  return base64UrlEncode(array);
}

// Tạo code_challenge từ code_verifier
async function generateCodeChallenge(verifier) {
  const encoder = new TextEncoder();
  const data = encoder.encode(verifier);
  const hash = await crypto.subtle.digest('SHA-256', data);
  return base64UrlEncode(new Uint8Array(hash));
}

// Sử dụng
const codeVerifier = generateCodeVerifier();
const codeChallenge = await generateCodeChallenge(codeVerifier);

// LƯU code_verifier trong memory/sessionStorage
sessionStorage.setItem('code_verifier', codeVerifier);
```

#### Bước 2: Authorization Request

```javascript
const authUrl = `https://authorization-server.com/oauth2/authorize?
  response_type=code
  &client_id=abc123
  &redirect_uri=https://myapp.com/callback
  &scope=read write
  &state=xyz789
  &code_challenge=${codeChallenge}           ← Gửi challenge
  &code_challenge_method=S256`;               ← Phương thức: SHA256

window.location.href = authUrl;
```

#### Bước 3: Token Request

```js
// Callback về app với code
const urlParams = new URLSearchParams(window.location.search);
const code = urlParams.get('code');

// LẤY lại code_verifier đã lưu
const codeVerifier = sessionStorage.getItem('code_verifier');

// Gửi token request
const response = await fetch('https://authorization-server.com/oauth2/token', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({
    grant_type: 'authorization_code',
    code: code,
    client_id: 'abc123',
    redirect_uri: 'https://myapp.com/callback',
    code_verifier: codeVerifier                ← Gửi verifier
  })
});

const tokens = await response.json();
```

## Bảng quy định:

| Loại Client                     | OAuth 2.0 (RFC 6749) | OAuth 2.1    | OAuth 2.0 Security BCP |
| ------------------------------- | -------------------- | ------------ | ---------------------- |
| **Public** (Mobile/SPA/Desktop) | RECOMMENDED          | **BẮT BUỘC** | **BẮT BUỘC**           |
| **Confidential** (Web backend)  | Không yêu cầu        | **BẮT BUỘC** | KHUYẾN NGHỊ            |

## Chi tiết:

**✅ BẮT BUỘC dùng PKCE:**

- ✅ Mobile apps (iOS/Android) - RFC 7636, OAuth 2.1

- ✅ Single Page Apps (React/Vue/Angular) - OAuth 2.1

- ✅ Desktop applications - OAuth 2.1

- ✅ CLI tools chạy trên máy user - OAuth 2.1

- ✅ Bất kỳ public client nào - OAuth 2.1


**✅ NÊN dùng PKCE (không bắt buộc OAuth 2.0):**

- ✅ Web apps có backend (confidential clients)

- Lý do: Thêm lớp bảo vệ chống authorization code injection

## 🔑 PHẦN 3: PASSWORD GRANT (RESOURCE OWNER PASSWORD CREDENTIALS) - Đã bị loại bỏ

### Tổng quan

**[CONFIDENT]** - Grant type này cho phép client **thu thập trực tiếp** username/password của user và gửi đến Authorization Server để lấy token.

⚠️ **CẢNH BÁO QUAN TRỌNG**: OAuth 2.0 Security Best Current Practice **KHÔNG KHUYẾN KHÍCH** dùng grant type này. OAuth 2.1 đã **LOẠI BỎ** hoàn toàn.

**Tại sao bị loại bỏ?**[](https://www.scottbrady.io/oauth/why-the-resource-owner-password-credentials-grant-type-is-not-authentication-nor-suitable-for-modern-applications)

1. **Vi phạm nguyên tắc cơ bản của OAuth**: User phải chia sẻ mật khẩu với client

2. **Không hỗ trợ MFA/2FA**: Không thể dùng xác thực đa yếu tố

3. **Không hỗ trợ SSO**: Không thể "Login with Google/Facebook"

4. **Rủi ro cao**: Client có thể lưu trữ password (phạm luật bảo mật)

5. **Phishing**: User quen nhập password vào app bất kỳ
### Nguyên lý hoạt động

```
┌─────────┐                                     
│  User   │                                     
└────┬────┘                                     
     │                                          
     │  1. Nhập username/password               
     │     TRỰC TIẾP trên form của Client       
     │     ⚠️ Client THẤY được password!
     ▼                                          
┌─────────┐                                     ┌──────────────────┐
│ Client  │  2. Client GỬI username/password    │ Authorization    │
│  App    │     đến Auth Server qua HTTP POST   │    Server        │
└────┬────┘ ──────────────────────────────────> └────────┬─────────┘
     │                                                   │
     │  3. Auth Server verify credentials                │
     │     (kiểm tra username/password đúng không)       │
     │                                                   │
     │  4. Trả về ACCESS TOKEN + REFRESH TOKEN           │
     │<──────────────────────────────────────────────────┤
     │                                                   │
┌────▼────┐                                     ┌────────▼─────────┐
│ Client  │  5. Dùng access token để gọi API    │  Resource Server │
│  App    │ ──────────────────────────────────> │                  │
└─────────┘                                     └──────────────────┘
```

**Sự khác biệt với Authorization Code Grant:**

| Authorization Code                            | Password Grant                              |
| --------------------------------------------- | ------------------------------------------- |
| User nhập password trên trang **Auth Server** | User nhập password trên form **Client App** |
| Client **KHÔNG THẤY** password                | Client **THẤY** password                    |
| An toàn ✅                                     | Nguy hiểm ❌                                 |
### Chi tiết kỹ thuật

#### TOKEN REQUEST

```http
POST /oauth2/token
Host: authorization-server.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Base64(client_id:client_secret)

grant_type=password
&username=john@example.com
&password=secret123
&scope=read write
```

**Các tham số:**

| Tham số      | Bắt buộc   | Mô tả                       |
| ------------ | ---------- | --------------------------- |
| `grant_type` | ✅ BẮT BUỘC | Phải là `password`          |
| `username`   | ✅ BẮT BUỘC | Username của resource owner |
| `password`   | ✅ BẮT BUỘC | Password của resource owner |
| `scope`      | ❌ TÙY CHỌN | Quyền truy cập yêu cầu      |
**Client authentication:**[](https://www.rfc-editor.org/rfc/rfc6749.html)​

- Confidential clients: Phải xác thực bằng `client_id` + `client_secret` (qua Authorization header hoặc request body)

- Public clients: Chỉ cần `client_id`
#### TOKEN RESPONSE

### Ví dụ thực tế

**Tình huống phù hợp**: Bạn xây dựng hệ thống microservices cho **NỘI BỘ công ty**:
- Frontend: Angular/React app
- Backend: Auth Service + Business Logic Services
- Tất cả do **cùng 1 tổ chức** sở hữu và bảo trì

**Quy trình**:
1. User nhập username/password vào form của Angular app
2. Angular app gửi credentials đến Auth Service
3. Auth Service verify và trả về token
4. Angular dùng token gọi các API khác

### ⛔ KHI NÀO KHÔNG NÊN DÙNG?

**[CONFIDENT]**

❌ **TUYỆT ĐỐI KHÔNG dùng khi:**
1. Client và Auth Server thuộc **khác tổ chức**
2. Third-party applications
3. Client không được user **TIN TƯỞNG TUYỆT ĐỐI**
4. Cần hỗ trợ Multi-Factor Authentication (MFA)
5. Cần delegated access (ví dụ: "Login with Google")

**Tại sao?**
- User phải **CHIA SẺ MẬT KHẨU** với client → Rất nguy hiểm!
- Client app có thể lưu password (violation!)
- Không hỗ trợ MFA, biometric authentication
- Nếu password bị đánh cắp, hậu quả nghiêm trọng hơn token bị đánh cắp

### ✅ KHI NÀO CÓ THỂ DÙNG?

**[LIKELY]**

Chỉ khi **TẤT CẢ** điều kiện sau được đáp ứng:
1. Client và Auth Server do **cùng 1 công ty** phát triển
2. User **tin tưởng tuyệt đối** client (ví dụ: mobile app chính thức của công ty)
3. **KHÔNG thể** dùng Authorization Code (ví dụ: legacy system đang migrate)
4. Là bước **TẠM THỜI** trong khi migrate sang Authorization Code

**Lưu ý**: Ngay cả khi đáp ứng các điều kiện trên, Authorization Code + PKCE vẫn là lựa chọn **AN TOÀN HƠN**.

## 🤖 PHẦN 4: CLIENT CREDENTIALS GRANT

### Tổng quan

**[CONFIDENT]** - Grant type này dùng cho **machine-to-machine authentication**, khi **KHÔNG có user** tham gia.

✅ **Phù hợp:**

- Backend service gọi backend service khác (microservices)

- Scheduled jobs/Cron jobs truy cập API

- CLI tools của admin/developer

- Ứng dụng daemon/background processes

- Health check endpoints

- Truy cập config server


❌ **KHÔNG dùng cho:**

- Truy cập tài nguyên của user cụ thể

- Web/Mobile apps cần user permission

- Bất kỳ thao tác nào "on behalf of user" (thay mặt user)

### Nguyên lý hoạt động

```
┌──────────────┐                              ┌──────────────────┐
│   Client     │  1. POST /token với          │ Authorization    │
│   Service A  │     client_id + secret       │    Server        │
│              │     grant_type=client_       │                  │
│              │     credentials              │                  │
└──────┬───────┘ ──────────────────────────>  └────────┬─────────┘
       │                                                │
       │  2. Auth Server xác thực client                │
       │     (verify client_id + client_secret)         │
       │                                                │
       │  3. Nhận ACCESS TOKEN                          │
       │     (⚠️ KHÔNG có refresh token)                │
       │ <──────────────────────────────────────────────┤
       │                                                │
┌──────▼───────┐                              ┌────────▼─────────┐
│   Client     │  4. Gọi API với Bearer       │  Resource Server │
│   Service A  │     access token             │   (Service B)    │
└──────────────┘ ──────────────────────────>  └──────────────────┘
```


**Điểm khác biệt quan trọng:**

| Authorization Code             | Client Credentials               |
| ------------------------------ | -------------------------------- |
| **CÓ user** tham gia           | **KHÔNG có user**                |
| User đăng nhập và đồng ý       | Client tự xác thực               |
| Access token đại diện cho user | Access token đại diện cho client |
| Có refresh token               | **KHÔNG có refresh token**       |
| Scope = quyền của user         | Scope = quyền của client         |
### Chi tiết kỹ thuật

#### TOKEN REQUEST

```http
POST /oauth2/token HTTP/1.1
Host: authorization-server.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Base64(client_id:client_secret)

grant_type=client_credentials
&scope=api.read api.write
```

**Các tham số:**

| Tham số      | Bắt buộc   | Mô tả                                                |
| ------------ | ---------- | ---------------------------------------------------- |
| `grant_type` | ✅ BẮT BUỘC | Phải là `client_credentials`                         |
| `scope`      | ❌ TÙY CHỌN | Quyền truy cập yêu cầu (Auth Server có thể giới hạn) |
**Client authentication:**[](https://www.rfc-editor.org/rfc/rfc6749.html)​

- **BẮT BUỘC**: Client phải xác thực bằng `client_id` + `client_secret`

- Có thể dùng HTTP Basic Authentication (khuyến nghị)

- Hoặc gửi trong request body (không khuyến nghị)
#### TOKEN RESPONSE

```json
{
  "access_token": "431eb294-bca4-4164-a82c-e08f56055f3f",
  "token_type": "Bearer",
  "expires_in": 7200,
  "scope": "api.read api.write"
}
```

⚠️ **Lưu ý**: KHÔNG có `refresh_token` vì không có user credentials để refresh.

### Ví dụ thực tế dễ hiểu

**Tình huống**: Hệ thống e-commerce của bạn có:

## 🔄 PHẦN 5: REFRESH TOKEN GRANT

### Tổng quan

**[CONFIDENT]** - Refresh Token cho phép client lấy **access token mới** mà **KHÔNG cần user đăng nhập lại**.[](https://oauth.net/2/refresh-tokens/)
### Tại sao cần Refresh Token?

**Vấn đề cần giải quyết:**

1. **Access token nên có thời gian sống ngắn** (1-2 giờ) để bảo mật

    - Nếu bị đánh cắp, thiệt hại giới hạn

    - Giảm thời gian kẻ tấn công có thể lạm dụng

2. **User không muốn đăng nhập lại liên tục**

    - Đăng nhập mỗi 1 tiếng = Trải nghiệm tồi tệ!

    - User sẽ bỏ ứng dụng

3. **❌ TUYỆT ĐỐI KHÔNG lưu username/password**

    - Vi phạm bảo mật nghiêm trọng

    - Vi phạm quy định (GDPR, PCI-DSS)


**Giải pháp: Refresh Token!**[](https://www.rfc-editor.org/rfc/rfc6749.html)

```
┌─────────────────────────────────────────────────┐
│  Access Token:                                  │
│  → Thời gian sống ngắn (15 phút - 2 giờ)        │
│  → Gửi đến Resource Server                      │
│  → Nếu bị đánh cắp: Thiệt hại giới hạn          │
│                                                 │
│  Refresh Token:                                 │
│  → Thời gian sống dài (7-30 ngày)               │
│  → CHỈ gửi đến Authorization Server             │
│  → Có thể THU HỒI (revoke) bất cứ lúc nào       │
│  → An toàn hơn việc lưu password                │
└─────────────────────────────────────────────────┘
```

**Lợi ích**:[](https://oauth.net/2/refresh-tokens/)​

- User không cần đăng nhập lại

- Access token ngắn → Giảm rủi ro

- Có thể thu hồi từng app riêng lẻ

- Không cần lưu password

### Chi tiết kỹ thuật

#### BƯỚC 1: Nhận token ban đầu

Khi dùng Authorization Code hoặc Password Grant, Auth Server trả về:

```json
{
  "access_token": "da2a4837-20a4-447d-917b-a22b4c0e9517",
  "token_type": "Bearer",
  "expires_in": 3600,  // 1 giờ
  "refresh_token": "221f5635-086e-4b11-808c-d88099a76213",
  "scope": "read write"
}
```

**Lưu ý:**[](https://www.rfc-editor.org/rfc/rfc6749.html)​

- Refresh token là **OPTIONAL** (Authorization Server quyết định có cấp hay không)

- **Client Credentials Grant**: KHÔNG có refresh token

- **Implicit Grant**: KHÔNG có refresh token (đã deprecated)

#### BƯỚC 2: Khi access token hết hạn

```http
POST /oauth2/token HTTP/1.1
Host: authorization-server.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic Base64(client_id:client_secret)

grant_type=refresh_token
&refresh_token=221f5635-086e-4b11-808c-d88099a76213
&scope=read  // ⚠️ TÙY CHỌN: Có thể giảm scope, KHÔNG được tăng
```

**Các tham số:**

| Tham số         | Bắt buộc   | Mô tả                                                                              |
| --------------- | ---------- | ---------------------------------------------------------------------------------- |
| `grant_type`    | ✅ BẮT BUỘC | Phải là `refresh_token`                                                            |
| `refresh_token` | ✅ BẮT BUỘC | Refresh token nhận được trước đó                                                   |
| `scope`         | ❌ TÙY CHỌN | Có thể giảm scope, KHÔNG được tăng[](https://www.rfc-editor.org/rfc/rfc6749.html)​ |

**Về scope parameter**:

```text
Ví dụ:
Token ban đầu: scope="read write delete"

✅ ĐƯỢC PHÉP:
  - scope="read"           (giảm xuống)
  - scope="read write"     (giảm xuống)
  - không truyền scope     (giữ nguyên "read write delete")

❌ KHÔNG ĐƯỢC PHÉP:
  - scope="read write delete admin"  (tăng thêm "admin")
  - scope="admin"                     (scope mới không có trong ban đầu)
```

#### 🔐 Refresh Token Rotation (Best Practice)

#### Vấn đề cần giải quyết

```text
Kịch bản tấn công:
1. User dùng app trên thiết bị A
2. Kẻ tấn công đánh cắp được refresh token
3. Kẻ tấn công dùng token từ thiết bị B
4. Cả user và kẻ tấn công đều dùng cùng 1 token
5. Authorization Server KHÔNG PHÁT HIỆN được!
```

#### Giải pháp: Refresh Token Rotation

**Cách hoạt động:**

```
Timeline:

T0: User login
    → access_token_1 (hết hạn T0+1h)
    → refresh_token_A (valid)

T1: User refresh (thiết bị A - hợp lệ)
    → Gửi refresh_token_A
    → Nhận access_token_2 + refresh_token_B
    → refresh_token_A BỊ VÔ HIỆU HÓA

T2: Kẻ tấn công dùng refresh_token_A (đã bị vô hiệu hóa)
    → Server phát hiện: "Token đã được dùng rồi!"
    → REUSE DETECTION: Có thể bị tấn công!
    → VÔ HIỆU HÓA TẤT CẢ: refresh_token_B, access_token_2
    → GHI LOG cảnh báo
    → YÊU CẦU user đăng nhập lại
```

#### Khi nào áp dụng Rotation?

| Client Type                            | Rotation Frequency | Lý do                              |
| -------------------------------------- | ------------------ | ---------------------------------- |
| **Public Clients** (SPA, Mobile)       | **Mỗi lần dùng**   | Không có client_secret, rủi ro cao |
| **Confidential Clients** (Web backend) | Khi đạt 70% TTL    | Có client_secret bảo vệ            |

#### 🛡️ Bảo mật Refresh Token
#### Best Practices

**1. Lưu trữ an toàn**[](https://www.iamdevbox.com/posts/how-oauth-21-refresh-tokens-work-best-practices-and-expiry/)​

```text
❌ SAI:
  - localStorage (dễ bị XSS)
  - sessionStorage (dễ bị XSS)
  - Cookie không có HttpOnly flag

✅ ĐÚNG:
  - Mobile: Keychain (iOS) / Keystore (Android)
  - Web Backend: Encrypted database
  - SPA: HttpOnly, Secure, SameSite cookies
```

**2. Transport Security**

```
✅ BẮT BUỘC:
  - Chỉ dùng HTTPS
  - Không bao giờ gửi qua HTTP
  - Không log refresh token
  - Không gửi qua URL parameters
```

**3. Token Lifetime**

```
Khuyến nghị:
  - Access token: 15 phút - 2 giờ
  - Refresh token: 7-30 ngày (tùy use case)

Cân nhắc:
  - App banking: 7 ngày (bảo mật cao)
  - App social: 30 ngày (trải nghiệm tốt)
  - App enterprise: 1 ngày (chính sách công ty)
```

**4. Revocation**[](https://www.iamdevbox.com/posts/how-oauth-21-refresh-tokens-work-best-practices-and-expiry/)

```
Khi nào revoke refresh token:
  ✅ User logout
  ✅ User thay đổi password
  ✅ Phát hiện hoạt động đáng ngờ
  ✅ User xóa thiết bị từ xa
  ✅ Admin thu hồi quyền
```

**5. Monitoring**

```
Giám sát:
  - Số lần refresh từ mỗi IP
  - Số lần refresh từ mỗi thiết bị
  - Failed refresh attempts
  - Token reuse detection events
  
Cảnh báo khi:
  - Refresh từ >2 IP trong cùng lúc
  - Nhiều failed attempts
  - Refresh token được dùng sau khi revoke
```

```java
    public void configure(ClientDetailsServiceConfigurer clients)

            .withClient("mobile-app")
            .secret("{bcrypt}$2a$10$...")

    }

        endpoints.authenticationManager(authenticationManager);
    }
```

### Best Practices

**[CONFIDENT]**

✅ **NÊN:**
1. Dùng refresh token với Authorization Code và Password grant
2. Access token: 15 phút - 1 giờ
3. Refresh token: 7 - 30 ngày
4. **Rotation**: Mỗi lần refresh, cấp refresh token MỚI
5. Lưu refresh token an toàn (encrypted storage)
6. Có cơ chế revoke refresh token

❌ **KHÔNG NÊN:**
1. Dùng refresh token với Client Credentials (không cần)
2. Refresh token thời gian sống vô hạn
3. Cho phép dùng refresh token đã expired
4. Lưu refresh token dưới dạng plain text
5. Share refresh token giữa nhiều devices mà không tracking

### Token Rotation và Security

**[LIKELY]** - Kỹ thuật nâng cao:

```
User login → Nhận RT_1
            ↓
1h sau: Dùng RT_1 → Nhận AT_2 + RT_2
                     RT_1 bị VÔ HIỆU HÓA
            ↓
1h sau: Dùng RT_2 → Nhận AT_3 + RT_3
                     RT_2 bị VÔ HIỆU HÓA
```

**Phát hiện token bị đánh cắp**:
- Nếu RT_1 được dùng **SAU KHI** RT_2 đã được cấp
- → Auth Server biết có token bị compromise
- → **Thu hồi TẤT CẢ** refresh tokens của user đó
- → Bắt user đăng nhập lại

### Hướng dẫn lựa chọn cụ thể

#### 🌐 Web Application (có backend)

```
Lựa chọn: Authorization Code
Lý do: 
- Client có thể giữ client_secret an toàn
- User không chia sẻ password với client
- Hỗ trợ MFA, SSO
```

#### 📱 Mobile App (iOS/Android)

```
Lựa chọn: Authorization Code + PKCE (BẮT BUỘC)
Lý do:
- Mobile app không giữ được secret (có thể reverse engineer)
- PKCE bảo vệ khỏi authorization code interception
- Tuân thủ OAuth 2.1 best practices
```

#### ⚛️ Single Page Application (React/Vue/Angular)

```
Lựa chọn: Authorization Code + PKCE
Lý do:
- JavaScript code chạy trên browser → không giữ được secret
- PKCE bắt buộc cho public clients
- Tuyệt đối KHÔNG dùng Implicit Grant (deprecated)
```

#### 🔧 Backend Service (Node.js/Java/Python API)

```
Lựa chọn: Client Credentials
Lý do:
- Không có user tham gia
- Service-to-service authentication
- Access non-user-specific resources
```

#### 🏢 Enterprise Internal Apps

```
Lựa chọn (ưu tiên):
1. Authorization Code (khuyên dùng)
2. Password Grant (chỉ khi bắt buộc)

Điều kiện dùng Password:
- Cùng tổ chức phát triển Frontend + Backend
- User tin tưởng tuyệt đối
- Đang migrate từ legacy system
- Kế hoạch chuyển sang Authorization Code
```

#### 📺 Smart TV / IoT Devices

```
Lựa chọn: Device Authorization Grant (RFC 8628)
Note: Không cover trong bài này, nhưng đây là chuẩn cho devices
```
